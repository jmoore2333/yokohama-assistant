## 2. The mechanism

### 2.1 The update path (F-1; R-F1, R-F3)

**What E left.** A returning visitor's first visit after a release is served the previous release by the old worker while the new one installs; the offer "A new version is ready. Reload to use it" renders on the door only (`web/src/OnThisDevice.tsx`, `Readiness`) and needs a click; the worker half (`web/src/sw.ts`) calls `skipWaiting()` only on the page's message and retains the previous generation, which is what keeps a tab that did not click working (PR #37, R-F2 and R-F5 of that cycle). The page half is `web/src/swRegister.ts` (`useReadiness`, `applyUpdate`, `readinessOf`). Nothing is stale at the edge: `/sw.js` and `/shell.bin` are `no-store` on both hosts.

**The client re-checks the release.** `useReadiness` calls `registration.update()` on `visibilitychange` to visible and on a 15-minute interval while the page is open. Each check is one fetch of `/sw.js` (29 KB, `no-store`), a static asset the Worker serves free (pricing footnote 3). The browser's own check on every page load stays. The interval is a named constant with a cell under fake timers; the focus path has a jsdom cell.

**The door applies a ready release itself.** When the route is the door (`web/src/route.ts`, `kind: "door"`; `useRoute` in `web/src/App.tsx`) and `readinessOf` reports a waiting worker beside an active one, the page calls `applyUpdate` — the SAME path the click takes, so the two "it has taken charge" events (`controllerchange` where the old worker controlled the tab, `activated` where nothing did) and the one-tab rule are unchanged. It fires at most once per page life (a ref), never on a first install (the offer needs a waiting worker AND an active one, `readinessOf`'s existing rule), and never while the route is not the door.

**Off the door, one passive line.** "A new version is ready. Reload to use it" is drawn on the lobby and the game screens as it is on the door, and the click is the only switch there. Its exact place on each screen is the orchestrator's call with a before-and-after picture (R-6.5c2.38's rule). Nothing reloads by itself while someone plays.

**Two tabs of one browser** (§9 F-7). `skipWaiting` is registration-wide: the door's apply hands EVERY tab the old worker controlled to the new one, and a game tab so handed over keeps running the old bundle out of the retained generation with `updateWaiting` now false — no line, and no way to learn it is behind. So a tab that hears a `controllerchange` it did not ask for sets a STALE state and draws the same line, whose click is a plain reload; the cell drives two hooks over one registration and reads the door reloading once and the game tab keeping its line until its own click. **And the door's auto-apply defers while a restore or a send is in flight** (§9 F-28): a busy flag set by the backup controls and the outbox's button holds the apply until they finish, so a person never loses a report to a reload.

**What makes the in-game click safe**, and the cell that pins it: a game open under release A, release B built and served, the line clicked, and the SAME game continues. A local game resumes from the browser's storage (the `offline.spec.ts` close-and-reopen cell is the precedent; that spec already produces a second release by re-running the precache generator over its own output); a table game rejoins by its link (E's arrival path); §2.3 keeps an old-bot game opening under a new build. The cell is an e2e over two releases of the local binary.

**The worker half is untouched.** `sw.ts`, `swRoute.ts` and `swInstall.ts` do not change; the update policy's worker half stays "skip-waiting only on the message, never `clients.claim()`".

**The guard gains a check** (`worker/scripts/deploy-guard.mjs`, check 10): a `cache` block whose `enabled` is not `false` — at the top level, in any `env`, or under `exports` — is refused, read as text and as values. With Workers Cache on, "requests served from the Worker's cache are billed at the same per-request rate as requests that invoke the Worker. This includes requests to static assets" (pricing footnote 4; `/workers/cache/`). Absent is off, since the block is an opt-in; the check refuses the KEY with any value but `false`. Check 5's pin of `run_worker_first` to `["/api/*", "/enter"]` stands.

**The readings, both hosts** (§3.3), with E's pinned-browser instrument committed as `web/scripts/pinned-browsers.mjs` (orchestrator-only; its state directory gitignored; no cookie VALUE ever written — the ledger copy's own rule): a browser pinned to E's release lands on the door and runs F's within seconds with NO click; a browser with a game open shows the line after a focus change; the door visit at zero invocations (§2.5).

**Not built:** no `release.json`; no forced reload in a game; no words fetched at run time. The self-host is identical by construction (the worker is the client's), and the reading is taken on the NAS too.

### 2.2 The release notice (R-F2)

**One build value, `YOKOHAMA_RELEASE_FEED`.** The URL the door reads for the latest release. Read as `web/scripts/build-values.mjs` reads the three (`BUILD_VALUES`), defined into the bundle by `web/vite.config.ts`, and given to the Docker build as an `ARG` beside the three in `deploy/Dockerfile`. Three states, spelled so "empty" and "unset" cannot be confused:
- **unset**: the default — when `YOKOHAMA_PROJECT_URL` names a GitHub repository (`https://github.com/<owner>/<repo>`, a trailing slash tolerated), the feed is that repository's latest-release endpoint (`https://api.github.com/repos/<owner>/<repo>/releases/latest`); when the link is anything else, or unset, there is no feed and no check;
- **a URL**: that feed (a fork points its own build at its own repository through its project link, or here);
- **the literal `off`**: no feed and no check.
The build scripts and the guides SET nothing for it, so the derived default is what a self-hoster gets; blanking it is `off`.

**The client reads it once per page life on the door and on the lobby**, and at most once an hour per browser after that (a timestamp in browser storage, every access wrapped, `chatFold.ts`'s idiom), which keeps a busy device inside the feed host's anonymous limit of 60 requests an hour. A cross-origin request: the service worker leaves it alone (`sw.ts`'s same-origin rule), the Worker never sees it, and offline or on any failure nothing is drawn and nothing retries within that page life. The read goes through its own seam (`web/src/releaseFeed.ts`, an injectable fetch), so the door's "asks the server nothing" cell (`FrontDoor.test.tsx`, the throwing `fetch` stub) keeps its meaning: no same-origin request.

**The comparison.** The feed's `tag_name` against the build's own workspace version, defined into the bundle as `__YOKOHAMA_VERSION__` from `web/package.json` (the cell `the_two_npm_packages_carry_the_workspace_version` holds that file to the workspace). Both parsed as `vX.Y.Z` triples; a tag that does not parse draws nothing, never a false alarm; equal or older draws nothing.

**The notice**: one quiet line on the door and on the lobby — "A newer release is available: v0.7.0. This site runs 0.6.0" — linking to the release's page (`html_url`, or the project link's releases page when absent). On the lobby it sits in the signed-in actions block beside the project link, the block a signed-in operator sees (§9 F-12); on the door under the blurb. Its exact place is the orchestrator's call with a picture (R-6.5c2.38). **The hourly throttle stores the ANSWER, not only the time** (§9 F-13): `{checkedAt, tag, url}` in browser storage, every access wrapped, and a stored newer answer under an hour old draws the notice with no fetch, so it does not vanish on a reload inside the hour.

**Both hosts, one mechanism.** The NAS and any self-host behave as the Worker does; the Worker's own door checks too, which is how the owner sees a tag the deployment lags.

**Proof** (§3.1): jsdom cells over a fixture feed — newer, equal, older, unparseable, blank — and the derivation of the default from the four link shapes. The repository is private today, so the feed answers 404 and the live reading records "no notice", correctly; the day the repository is public the check works with no change.

**Not built:** no server-side check, no notification of anyone, no self-updating server. The self-host guide gains an "Updating" section and `deploy/update.sh` (§2.9).

### 2.3 The resume rule (R-F4; amends R-6.5c2.10 forward; corrected after the adversarial review, §9 F-1, F-5, F-6, F-8, F-9)

**What R-6.5c2.10 built, and what it costs.** `crates/yokohama-web/src/bots.rs` marks a bot seat FOREIGN when its recorded `(controller, version, params)` differs from `production()`, the descriptor of `bot::PROVISIONAL_DEFAULT_BOT`; `Games::live_handle` (`games.rs`, the rule's one site) refuses to open a game that is not over with a foreign seat. The CLI's resume (`crates/yokohama-cli/src/bot.rs`, `BotSeats::from_provenance`, public) rebuilds every recorded bot through `Contestant::from_parts` and `eligible`; a seat `eligible` refuses resumes as a HUMAN with a warning; a seated bot whose version or ANY knob — the weights digest of a named identity among them — differs from what this build derives gets a drift WARNING and still plays (`identity_drift_warnings`, `bot.rs:482–507`). **And `eligible` admits exactly ONE named identity, the one the driver ships, by equality with `Contestant::PRODUCTION`; every other named identity is refused as "a named research identity for arena weight comparisons, not available as a CLI bot" (`bot.rs:377–403`), by a stated decision: admitting a seat "is a decision for whoever wants that seat, made then".** So the web cannot widen its own predicate past the CLI's: it seats through `Repl::new` → `from_provenance`, and a seat the CLI converts to a human is a seat nobody moves. The day V5 ships as a new named identity (the identity freeze's rule for a new weight table), V4 becomes ineligible in the CLI too.

**The rule, as F builds it.** The web decides foreignness by the CLI's OWN resume, called through its public surface, so the two can never disagree: `BotSeats::from_provenance(record.run)` is called once; for every seat the record names a bot for, `contestant_at(seat)` is `None` (the CLI would convert it) → FOREIGN with the CLI's reason; `Some(_)` beside a drift warning naming that seat (a version, or any knob, the weights digest included) → FOREIGN as drift, in the warning's own words; otherwise the build runs that EXACT bot and the game opens with it playing its seat, whatever the production bot is. The reasons are the CLI's sentences with their resume tails cut ("— it resumes as a HUMAN seat, so you are now playing it"; "— the seat still plays, under the CURRENT build"), pinned by a cell that holds the CLI's three sentence shapes, so a change of the CLI's wording fails the web's cell rather than silently changing a refusal. **No CLI change, no seam change: `eligible` stays `pub(crate)`.**

**What this means the day V5 ships.** Under this rule the web follows `eligible` by construction. A V4 game opens under a V5 build EXACTLY WHEN the V5 ship grandfathers `v4-step9-draft1` in `eligible` — one arm: the production identity and every identity that was production — a CLI behaviour change that belongs to the AI lane's V5 cycle, not to F's fence. F records that requirement in the AI lane's re-entry handover as the ONE line the V5 ship owes, and the lane document says it in its by-design list. Until then the rule's visible effect is on the grandfathered controllers (`lookahead-v1`, `greedy-v1`, the rungs), which R-6.5c2.10 refused and this rule plays on, and on every refusal sentence, which now names why. The owner's ruling, "a V5 build can still play V4", is met by F's half plus that one line; this specification says so rather than claiming it done.

**New games deal only the production bot**, as today: an undealt table, the door's bot card and the table form name `PROVISIONAL_DEFAULT_BOT` through the contract file `web/src/wire/production_bot.json`; nothing on the web offers an older identity.

**`runs_here` on the wire** (`TableBot.runs_here`, `bots::table_bot`) means the same predicate, so a table dealt to a bot this build runs reads its label in the lobby and opens.

**Every refusal stays, with its reason.** The authored sentence is `This game was played against {played}. This server can't continue it: {why}`, where `{why}` is the CLI's clause — "{name} is a named research identity for arena weight comparisons, not available as a CLI bot"; "{name} … which this build does not know how to run ({from_parts}' sentence)"; "records {key}={a}, but this build derives {key}={b}"; "records controller {name} at version {a}, but this build runs version {b}" — and `{played}`/`{runs}` keep the versioned and knobbed distinguishing labels of cycle C; the `why` refusal for a move by a foreign bot stays (the thirteenth refusal shape); a `SEMANTICS_REV` mismatch keeps "Will not open here" with export and remove; **no compatibility shim for an older rev ever enters the web build**.

**The CLI is untouched**: it still resumes an unrunnable seat as a human with its warning; the web never converts a seat.

**What moves**: `bots::foreign` (now `Vec<(u8, BotDescriptor, String)>`, the reason carried), `bots::runs_here`, `table_bot`, the sentence; the one site in `games.rs`; the lobby's wording where `runs_here` is false. **The corpus's foreign samples are ALREADY the V5 shape**: `wire_fixtures.rs` builds them from `v2-padded`, a non-production named identity that stays foreign under this rule; they are regenerated ONLY for the new sentence, the diff read for exactly that (a regenerated corpus freezes a leak as faithfully as a fix). The unit fixture `foreign_pair("lookahead-v1", …)` is a MONGREL — a renamed seat that keeps V4's weights digest — and becomes the named DRIFT refusal; the opens case is a record built from `Contestant::LookaheadV1`'s own full descriptor. The browser module follows, being the same layer.

**Cells** (§3.1): a genuine `lookahead-v1` game resumes under the production build and its bot makes the next move; `v2-padded` refuses with `eligible`'s own sentence — the V5 shape, pinned; the mongrel refuses as drift naming the `weights` key; a version drift refuses naming both versions; a named identity at knobs it never had refuses with `from_parts`' sentence; a finished foreign game opens as today; `why` on a move by a runnable non-production bot reconstructs it by replay; the three CLI sentence shapes are held verbatim.

**Fences**: no engine file, no CLI file, no bot behaviour, `SEMANTICS_REV` 7; the change is the layer's rule about which recorded bot it seats, decided by the CLI's own resume. Recorded as a ruling amending R-6.5c2.10 forward, with the V5 requirement as one line in `docs/plans/2026-09-11-ai-lane-reentry-handover.md`; the naming rule of the identity freeze is what keeps continuation honest.

### 2.4 The self-host sweep (F-2; R-F9, R-F10)

**What E left.** The axum host reads no TTL, no table expires there, `/api/health` says so (`table_ttl_days: null`, `open_table_ttl_days: null` — `api::Host` and `HealthView` in `crates/yokohama-web/src/api.rs`), and `deploy/README.md` §8 is the by-hand recipe.

**Two launch variables, the Worker's names and meanings** (`worker/src/config.ts`'s rules, restated on the axum host):
- `YOKOHAMA_WEB_TABLE_TTL_DAYS`: whole days above zero a table stands idle before it expires; unset means no sweep, today's behaviour;
- `YOKOHAMA_WEB_OPEN_TABLE_TTL_DAYS`: whole days above zero, default 7, inert without the first, for a table whose status is still `open` (a seat unfilled); a `dealing` table waits the first, as on the Worker (E's ruling 9-b).
A bad value stops the server at start naming the variable (the chat variables' shape, `main.rs`).

**Activity** is the latest write among the game's three documents — the record, the table and the chat — read as their modification times; the same three the Worker folds its `written_at` stamps over. The `Store` trait (`crates/yokohama-web/src/store.rs`) gains one read, `last_written(id) -> Result<Option<u64>, String>` (unix seconds), **with a default body answering `Ok(None)`** — "activity unknown: never a candidate", so the twenty test doubles across the crate keep compiling and a table whose activity nobody can read is never ended (a cell says so); `FsStore` reads the three files' metadata, `MemStore` stamps writes for the cells (§9 F-10). The house chat is never a table (`is_the_house`). **A race, named** (§9 F-25): the pass decides from `last_written` and then calls the creator's delete, which re-checks the seat and the creator but not idleness, so a move landing in the seconds between is refused out loud and the game is archived, not lost; the lane document's by-design list says so.

**The sweep** is a tokio interval task started in `main.rs` beside the server: hourly, the first pass one minute after start. Each pass:
1. lists the tables (`Store::list(Doc::Table)`), reads each document's status and activity, and decides through ONE pure function (`sweep::ending(status, last_active, now, ttl, open_ttl) -> Option<Ending>`), the mirror of the Worker's `expiryReason`;
2. logs one line per table it is about to end — id, status, idle days, reason (`expired` or `waited`) — BEFORE ending any;
3. ends each through the same layer delete the creator's Abandon uses (`Games::delete(id, &creator)`, the creator read off the table document, `TableDoc::created_by`; the Worker's `expire` shape), so a finished game already stamped is never put twice, a mid-play game lands under `abandoned/`, an open table with no game archives nothing, and a failed archive put REFUSES the delete and keeps the table for the next pass (the existing rule);
4. logs each ending with where the copy went.

**A TTL with no archive directory refuses to start**, naming both variables: a sweep that discards games is not a configuration this host offers. Stricter than the Worker (whose marker says "this server keeps no archive"), by choice.

**No marker** (R-F10): a removed table answers "no such game" as today; the log line is the record. The lane document's §15 names the divergence.

**`/api/health` reports both values** as the Worker does, `null` when unset; the wire corpus's `health.json` is unchanged because the corpus host sets none.

**Where it lives**: the decision in a pure module beside the task (`crates/yokohama-web/src/sweep.rs`, no platform call, tested without tokio) — `Ttls::from_lookup(lookup: impl Fn(&str) -> Option<String>)` is pure and `main.rs` passes `std::env::var`; the task (`run`, with its `SystemTime` read) sits in ONE column-0 `#[cfg(feature = "server")]`-gated region at the END of the file, closed by the `// ---- end server ----` marker, because the scan `platform_calls_stay_behind_the_server_feature` gates only column-0 items after the attribute and reports every ungated item inside a region (§9 F-11, measured against the real scan).

### 2.5 The door unmetered (F-3; R-F5; corrected after the adversarial review, §9 F-2, F-20, F-21, F-29, F-30, F-31)

**The fence, stated once.** On the Worker a door visit with nothing owed, a local game to its end, and any request for a path the release does not serve cost zero invocations; the first metered request is `/enter` behind the multiplayer button, a link arrival's first API read, or a finished local game's archive upload (a door visit that still owes an upload drains it, by design). Pinned three ways: the guard on the configuration (§2.1's check 10, the checks below), an e2e cell on the client, and the live reading.

**What the platform does with a miss, from Cloudflare's own routing diagram** (`developers.cloudflare.com/workers/static-assets/routing/static-site-generation/`, read 2026-09-30): a request matching a positive `run_worker_first` pattern goes to the Worker; one matching a NEGATIVE pattern goes to the asset layer; otherwise an asset that exists is served; otherwise, with a Worker script present, **a request that is not a navigation (`Sec-Fetch-Mode: navigate`) INVOKES THE WORKER whatever `not_found_handling` says, and only a navigation reaches the asset layer's fallback** (the compatibility flag "Navigation requests prefer asset serving", default since 2025-04-01). Negative patterns take precedence over positive ones (`/workers/static-assets/binding/`), so no `!/*` can free the root without taking `/api/*` from the Worker. The M6.5c spike measured the same fact (its spec §0.3 row 7). **So a static 404 page keeps a BROWSER's miss off the Worker and does nothing for a SCANNER's**, whose probes carry no navigation header, and E's zero was a door VISIT's, never a probe's. One caveat the two routing pages leave open: the SPA page says the ARRAY form of `run_worker_first` "disables the automatic `Sec-Fetch-Mode: navigate` detection"; whether a navigation miss under this deployment's array reaches the asset layer or the Worker is what the probe reads (§2.6's window).

**The lever is the edge, and it is §2.6's rule.** ONE WAF custom rule on the Worker's hostname challenges every request whose path is not one of the release's own static names — the root files (`/`, `/index.html`, `/sw.js`, `/shell.bin`, `/manifest.webmanifest`, `/404.html`, `/robots.txt`, `/llms.txt`, `/sitemap.xml`, `/build-values.json`) and the prefixes (`/assets/`, `/art/`, `/icons/`, `/fonts/`, `/help/`, and Cloudflare's own `/cdn-cgi/`). Everything else — `/api/*`, `/enter`, `/.env`, `/wp-login.php`, a random path, a HEAD or OPTIONS to any of them — is decided at the edge, in the `http_request_firewall_custom` phase, before rate limiting, Bot Fight Mode and the Access check (`/ruleset-engine/reference/phases-list/`), at zero invocations. Its expression is DERIVED from the assets tree by a committed script with a drift cell, so a release that adds a top-level name fails the cell until the rule's expression is regenerated (§2.6 names the script). The rule is the no-Access deployment's fence; under Access it is off, because Access already keeps every stranger's request off the Worker and the live tiers' service token cannot pass a challenge.

**The 404 page stays, as a courtesy and for parity.** A static `404.html` in `web/public/` (the project's own words, a link home, `<meta name="robots" content="noindex">`) and `not_found_handling` set to `404-page` in `worker/wrangler.jsonc`'s assets block and in the pool's two copies; the guard's check 5 is amended to that value and a new check (11) requires the file in the assets tree. A browser that navigates to a typo, or that the rule has just cleared, sees the page instead of a blank. Spec §2.3 of the M6.5c objects spec is corrected forward here: the value it chose was right for the install and cannot be the fence.
- **Why the install tolerates it**: the worker checks every entry's status and content type (`swInstall.ts`'s `checkHead`), so a 404 page fails an install as honestly as an empty 404 did; and a controlled browser never sees it, since the worker answers every navigation from the shell (`swRoute.ts` rule 2).
- **The axum host** serves the same page for a miss that carries an extension, for parity (`assets.rs`'s `serve_path`); its extension-less fallback to the shell stays, since the client's routes are hash-only and a self-host has no edge.
- **Not precached**: the 404 page, the build-values stamp and §2.7's presence files are excluded by the precache generator's walk (`web/scripts/precache.mjs`, the `distFiles` filter), so the offline count is unchanged. The assembler copies `web/dist` whole and refuses a path two sources provide, so it needs no edit; a cell reads that the files land in the tree.

**The probe** runs in the window (§2.6), with the rule ON: scanner-shaped requests for `/.env`, `/wp-login.php`, `/admin`, `/xmlrpc.php` and a random path in THREE shapes — a bare client; a browser User-Agent with `Sec-Fetch-Mode: navigate` and `Accept: text/html`; a browser User-Agent with `Sec-Fetch-Mode: no-cors` and `Accept: */*` (the shape a scanner impersonating a browser sends, and the one Bot Fight Mode's answer cannot be confused with) — read against the Observability query API's stateless count over the probe's own minute (`worker/RUNBOOK.md` §7's method), beside a control read that proves the instrument counts (one `/api/health` from a cleared browser in its own minute reads one). Zero is the pass. The zone's Bot Fight Mode setting is read into the record so a `cf-mitigated` answer is attributed to the rule and not to it.

**`/api/health` joins the protected paths** for a state-2 door: `worker/scripts/access-paths.mjs` stops excepting `health`, its drift cell follows, and the lane document's §8 list changes. The lobby reads health after `/enter`; the deploy's smoke and any uptime probe carry the service credential, or watch `/` (a static asset).

**The ledger** is a new lane-document section, "The metered-action ledger": one row per request the client can make to the server, with its route, its trigger (the screen and the action), its purpose, its count per session or per applied move (E's figures — 7.9 requests a move, 8.6 per event with the setup in — and F's tally from `web/e2e/harness.ts`'s `YOKOHAMA_WEB_TALLY` through `web/scripts/tally-report.mjs`), whether it can happen before a clearance (§2.6), and whether a script could make it without a browser. A cell in `crates/yokohama-web/tests/lane_document.rs` holds every route of the router to a row; the section's row parser is the API map's, parameterised for the ledger's columns. **The caveat, recorded in the section's first paragraph**: the totals are the harness's — the two-browser tier's watcher, the replay's forces — and the value is the actions and their ranges, for the wrap's own analysis and for anyone hosting it. One row the ledger must carry from the start (§9 F-14): under the open door a visitor who never chose a name finishes a bot game and, as E left it, spends a health read and an archive post to be told `signed-out`; §2.6 removes the post.

**The fence cell** (`web/e2e`): the door makes no same-origin request beyond the release's own files (no `/api/`, no `/enter`, no unknown path); a local game makes none before its upload; a request for `/wp-login.php` is answered 404 with the page, in an uncontrolled context as a navigation too, while a controlled context's navigation gets the shell. Against the local binary the axum host answers; the Worker's behaviour is the live reading.

### 2.6 Turnstile and the public window (F-4; R-F6, R-F7; corrected after the adversarial review, §9 F-2, F-3, F-4, F-15, F-16, F-23, F-26, F-27, F-31)

**What it can and cannot buy, by door state.** Under today's hostname-wide Access nothing reaches the Worker without a login, so a widget prevents no invocations. Under a state-2 door (the door public, the API behind Access) the same, with `/api/health` closed by §2.5. Under a state-1 door (no Access, the owner's end state) every API path is metered and public, and a script skips the door's button and calls `/api/*` directly; and under the open door `/enter` mints nothing — it is a 302, and the caller is a claimed name on every API call. **So the protection is not the button and not `/enter`: it is an EDGE rule, and the widget is how a person passes it once.**

**The rule is the fence and the definition of the no-Access shape.** ONE WAF custom rule on the `moore.nyc` zone (five on Free; every action but Log; `starts_with()` and set membership are in the rules language, regular expressions are not): Managed Challenge on `http.host eq "yokohama.moore.nyc"` for every request whose path is NOT one of the release's static names — §2.5's root files and prefixes, `/cdn-cgi/` among them. It subsumes `/enter` and `/api/*`. Its expression is printed by a committed script, `worker/scripts/edge-rule.mjs`, from the assets tree's top-level names, as the rule's JSON (`expression`, `action: "managed_challenge"`, `description`), with a drift cell pinning the list to the tree, and a `--verify` mode that compares a rule read from the zone (the orchestrator reads it through the API and pipes it in) to the tree's; the rule is created through the API as the rate-limit rule was and kept by its id. **Enabled with the no-Access state and DISABLED under Access**: the live replay's and the live tier's service token cannot pass a challenge, and under Access every stranger is already stopped at the edge. **The order at the flip**: the rule ON before the hostname comes off Access; on the revert, Access back BEFORE the rule goes off, so the API is never open and unchallenged for a moment.

**Pre-clearance is how a person passes the rule.** The widget (mode `managed`, pre-clearance ON at level `managed`, the widget's hostname the Worker's; the owner's existing widget confirmed for those three before anything is built, through `wrangler turnstile widget get` with `WRANGLER_WRITE_LOGS=false WRANGLER_LOG=log WRANGLER_LOG_SANITIZE=true`, the secret field never selected) issues the zone's `cf_clearance` cookie when a person passes it; every later same-origin request — the lobby's fetches, the stream, the WebSocket upgrade, the archive post — carries it past the rule for the zone's Challenge Passage duration. It renders on demand only, from `challenges.cloudflare.com/turnstile/v0/api.js` (cross-origin, so `sw.ts` leaves it alone; never at door load, never precached, nothing on the offline door but a sentence that the lobby needs a connection), at exactly these moments:
- **the multiplayer button**: the widget in the friends card on the click; on success the plain GET navigation to `/enter` proceeds as today. **`/enter` is unchanged on both hosts** — a 302 to the lobby, no token read — because the token grants nothing here: the cookie does, and a Worker-side siteverify would cost an invocation to protect nothing (§9 F-3). Siteverify is NOT built, no secret is set, and the Turnstile dashboard's "no siteverify traffic" banner is expected and documented. Every other `/enter` link in the client (the outbox's "Sign in at the door", the door's and the refusal screen's) stays a plain navigation: a stranger's meets the Managed Challenge interstitial, which a browser passes on its own, then the 302.
- **a challenged fetch**: Cloudflare answers a challenged fetch 403 with `cf-mitigated: challenge` (readable by a same-origin `fetch`), and its guidance for single-page applications is to render the pre-clearance widget then and retry. The client has THREE fetch sites and a socket (`api.ts`'s `call`, the record download, `sse.ts`'s stream reader, `ws.ts`'s upgrade); the challenge is detected at each through ONE predicate, the widget rendered once in an overlay ("Checking that this is a person…"), the request retried once; a second challenge on the same request is the refusal it is. A stream or a socket that fails on a challenge makes one `call` to pass the check and reconnects through its existing ladder, so a watcher who makes no other call is not stranded. With no site key in the build, a challenged fetch is the ordinary error path at once, naming the edge.
- **the outbox**: a challenged send inside a non-interactive drain (the `online` event, a background launch) — the archive fact's health read included, which is a fresh context's FIRST request — marks every waiting row "waiting for a human check"; the widget renders for them only in a visible tab from a launch or a click (the door's pending row offers it), never in a hidden tab; a landed retry clears the row as today. And a visitor under the open door who has chosen no name marks a finished game `signed-out` locally, with no post: the layer's refusal is certain, and the ledger (§2.5) records the path.

**Two settings, one guard.** `YOKOHAMA_TURNSTILE_SITEKEY`, a client BUILD VALUE (the site key is public by nature): blank draws today's plain link and loads no script — the NAS build's case. `YOKOHAMA_TURNSTILE`, `on` | `off` in the deploy configuration's `vars`: a DECLARATION read by the deploy guard and the post-deploy smoke, never by the Worker at run time — `off` in `wrangler.jsonc` and `wrangler.gate.jsonc`, `on` in `wrangler.open.jsonc`. The guard's check 12 holds it to the build's stamp (`build-values.json`, R-FP3): `on` exactly when the bundle carries a site key, `off` exactly when it does not; so each door state is its own client build (production, Access on, built without the key; the open configuration with it; the NAS never). **The post-deploy smoke closes the gap the reviewer named**: after any `on` deploy, a cookie-less `GET /api/health` must read 403 with `cf-mitigated: challenge`, or the deploy FAILS its smoke — a switch that says `on` over a missing rule is not a state this project ships. Under hostname-wide Access a keyed build works and merely renders a needless widget; under state 2 the same; both stay `off` by R-FP4. The `TURNSTILE_SECRET` line the owner put in the repository root's `.dev.vars` is unused by F and may be deleted; it is inert either way.

**The clearance's lifetime is the zone's Challenge Passage**, a zone-wide setting governing every host on `moore.nyc` (Cloudflare: the widget's cookie "will be valid for the time specified by the zone-level Challenge Passage value"; Precursor may re-challenge a session it finds suspicious regardless). The pre-flight reads the current value into the record; the end state wants one at least a game's length, and the owner sets it. A lapse mid-game meets the fetch handler at the next request and the game continues.

**Residuals, named** (§9 F-31): a clearance a person solved can be reused by a script on the same machine until it lapses (Cloudflare recommends a rate-limit rule keyed on the cookie's value; whether the Free plan's one rule can be keyed so is PLAUSIBLE and unread); a Free-plan day that exhausts its Worker requests answers the Worker's paths 429 while the assets keep serving, so the door stays up and multiplayer stops (the billing page); Cloudflare's managed `robots.txt`, if on for the zone, PREPENDS its own block to the served file, so the deploy reads the served body.
