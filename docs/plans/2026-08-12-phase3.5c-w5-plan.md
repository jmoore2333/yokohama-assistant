# Phase 3.5c minimal W5 — implementation plan

> **For agentic workers:** execute task-by-task under the repo's standing 3.5c cadence (fresh Opus implementer per task at xhigh → independent Opus reviewer → orchestrator adjudicates, fix wave in its own commit, ledger update) — that cadence is owner-ruled and supersedes generic plan-execution skills. Steps use checkbox syntax for tracking. Every implementer re-verifies anchors at its own HEAD before editing (HEAD-guard discipline); the orchestrator never touches the tree while an implementer runs.

**Goal:** CLI bot seats typed to `Contestant` playing the production-intent `lookahead-v1` by default, a `why` command that reconstructs and explains every CLI bot move, and the `state_at` replay-to-position substrate — D4's minimal cut, Phase A of the ratified scoping amendment.

**Architecture:** two additive core surfaces (`Contestant::from_parts`, `record::state_at`) feed a four-seam CLI retype whose single `decide` path serves both the bot pump and `why`; `why` reconstructs decisions by replaying the record to position and re-running the recorded contestant under the preserved `(bot_seed, events.len())` keying, refusing on any mismatch. Spec: `docs/plans/2026-08-12-phase3.5c-w5-design.md` (all §-references below point there).

**Tech stack:** the existing workspace only — no new dependencies.

```rust
impl Contestant {
    /// Inverse of `descriptor()` over the record's (controller name, params) halves.
    pub fn from_parts(name: &str, params: &BTreeMap<String, i64>) -> Result<Contestant, String>;
    /// The display echo `name@vN{k=v,…}` (NOT the parse grammar; no FromStr round-trip).

```

**`from_parts` contract (design §1.5):** the `name` half matches the controller consts (`GREEDY_CONTROLLER`, `LOOKAHEAD_CONTROLLER`, `ATOMIC_DIAG_CONTROLLER`, `MCTS_CONTROLLER`, and the three rung names via `RolloutPolicy`); construction knobs come from `params` using the DESCRIPTOR's key names (read them from `controller_provenance`/`RolloutPolicy`'s descriptor source, not from the grammar's token names); an absent `cap` key ⟹ `cap: None`; the known identity keys (`eval_impl`, `weights`, `placement_cap`) are accepted and NOT consumed as construction inputs; any other unknown key, unknown name, or out-of-range value is `Err(String)` naming what was seen. A missing construction key takes the arm's default const value only where `descriptor()` itself would omit it — if the descriptor always emits the key (verify per arm), a missing key is an error, not a default. Core stays neutral: `from_parts` parses diagnostics (`mcts-v1`, `atomic-diag-v1`) without complaint — eligibility is the CLI's business (task 3).
