## T2 — extended score tables: the L2 "17th-column" machinery (spec §4.1 item 2, §4.2) — code task

**Files**: modify `crates/yokohama-core/examples/eval_probe.rs` only (`ScoreTableSpec`,

**Produces:**
```rust

                        extensions: Vec<(CandidateColumn, i64, i64)> }  // (column, early, late)
// grammar: <name>=<base>[+<column>=<e>/<l>]…   base ∈ v1|v2|v2-draft|<16 i64>/<16 i64>
// parse rule (spec §4.1): strip extension clauses greedily from the RIGHT while the suffix
```

**Content:**
1. Parse per the grammar above; refusals name what was seen (unknown column, malformed
   clause, leading-`+` vector entry). `v1`/`v2`/`v2-draft` bases keep byte-identical
   round-command compatibility (zero extensions == today's parse; pin it).
2. Evaluation: `candidate_total` gains the extension terms — per clause,
   `interpolate(e, l, progress)` times (viewer's column value − the opponent-extreme rule
   applied to the column, reproducing the mirror's signed-weight first-wins convention) —
   exactly a feature's pricing, so an extension table IS the admission preview (spec §4.1).
   Terminal short-circuit unchanged (extensions contribute nothing at terminal views, as a
   real feature wouldn't).
3. **Reproduction pins:** (a) `<name>=v2+<any column>=0/0` reproduces the plain `v2` row
   cell-for-cell on a small corpus (a zero-weight extension is inert); (b) the existing
   `the_candidate_machinery_with_v1_reproduces_the_benchmark_row` pin stays green
   untouched.
4. **The improvement interval (spec §4.2 / register #5):** for an extension table whose
   base is a named table, print beside its held-out per-stage AUC the PAIRED-DIFFERENCE
   held-out bootstrap interval vs its own base (same game-clustered resamples applied to
   both, difference per resample) — the line a noise-level L2 pass is visible in.
5. **Data contact (GREEN evidence)**: one release run at the T1 scratch master with
   `--score-table v2 --score-table probe1=v2+terminal_margin_now=4/4` (any rung); report
   the base-reproduction check and the printed improvement interval, sanity-read.
6. Costs stay sane: extensions price on the already-derived structure; note the measured
   per-run wall in the report.

## Task sequencing, contractions, and review cadence

T1 → T2 → T3(GATE) → [T4 → T5 → T6](first survivor) → [T7 → T8 → T9](second survivor) →
T10 → T11 → T12, strictly sequential (shared files/module chains; the orchestrator never
overlaps an implementer). Contractions at the T3 gate: one survivor ⇒ its trio runs in the
T4–T6 slot with the width move, T7–T9 skipped; zero survivors ⇒ jump to T12's null close.
A T6/T9 adoption failure reverts that candidate's commits and proceeds as if washed
(recorded). Each code task: fresh Opus-max implementer (RED commit → GREEN commit), then a
fresh Fable-max reviewer (re-derive arithmetic, re-run suites, mutation probes with
escapes named), orchestrator adjudication, fix wave if findings demand. ~50-minute monitor
wakeups per dispatch, reset on report-back. The adjudicator lane (spec §10) dispatches
only after T10 lands. The whole-branch Fable review at T12 is the last gate before merge.
