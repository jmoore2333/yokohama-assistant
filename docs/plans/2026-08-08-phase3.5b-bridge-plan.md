## §0. Corpus facts measured while writing this plan

Measured against `bridge-captures/895724349.ndjson` on 2026-08-08 (gitignored; 491 lines = 488 `packets` + 3 `snapshot`, 1.85 MB). These are the facts the task list is shaped by — each is re-derivable from the file, and a task that assumes one states it as a checked precondition rather than as knowledge.

1. **Two feeds, and the catch-up feed is the POORER one.** Four `xhr` `notificationHistory` responses (`from=2/17/112/213`); the fullest holds 187 packets over `move_id` 13..194, and the union of the four covers **1..194 with no gaps**. 484 `websocket` frames on `wss://ws-x3.boardgamearena.com/connection/websocket` cover **107..194 only** (88 of 194). **The history feed's notification `args` are LOG-shaped; the socket feed's are STATE-shaped.** `presidentPlacement` in history is `{action, player_id, player_name, power, tile_name}`; the same event on the socket adds `pres_tile_key`, `trg_tile_key`, `route_keys`, `workers`, `player_workers`, `counters`. `resourceChange` in history carries `{player_id, player_name}` and **nothing else** — the quantity and the good live only inside the pre-rendered `log` string ("gains: 2 &lt;B&gt;Tea&lt;/B&gt;") — while the socket form adds `result_info {tea, fish, silk, copper, yen, vps, gain_text}` and `tile_key`. `orderRefresh` in history names no card; on the socket it carries `order_card` in full. **H2's catch-up translator therefore cannot be a field-copier; it is a constraint filter over the engine's own legal list.**
2. **Supersession is a LIVE-feed problem, already solved in the history feed.** In the fullest history response `move_id` is strictly monotone with no duplicates, and the nine `undoRestorePoint` notifications sit in it as markers with no superseded packets around them — BGA collapses before it serves. The socket feed carries the raw regressions the ledger banked (**118→117, 123→122, 148→147**). `packet_id` ≠ `move_id` (packet 28 carries move 27), and packets with `move_id: null` and an EMPTY `data` array exist (five in the fullest response).
3. **The order vector is a perfect key, and country is a free second opinion.** All 36 of our order requirement+reward vectors are distinct **even without country** (re-verified against `data.rs`), so country is redundant — which is exactly what makes it a tripwire. The corpus contains **20 distinct BGA order rows; all 20 match exactly one of our 36, zero unmatched, zero ambiguous**, and the BGA country code maps bijectively across those 20 (1 American · 2 German · 3 French · 4 Dutch · 5 English). **The design §1 permutation pairs, measured on the OTHER table (#895608640, now expired), reproduce here exactly** — their 5→O21, 10→O17, 11→O09, 21→O20, 28→O32 — so the permutation is a property of BGA's data and not of one table.
4. **The tech identity is NOT derivable and must be ledgered.** `(country, req_gears)` does not identify a title: English/3 alone is `{Postal System, Ball, University, Stagecoach}`, and there are six such colliding buckets over the 20 titles. Names arrive only in `techAcquisition`'s `tech_name`, and only the SOCKET form of that notification also carries `tech_card.tech_id`. **This corpus proves exactly one row: `tech_id 2 = "Mining Technology"` (country 2, req_gears 3).** Twenty-nine remain unknown. H0's negative result stands — there is no bulk static card table client-side.
5. **This corpus has no game-start observation, and that bounds the acceptance run.** The earliest `gamedatas` snapshot is mid-game (`gamestate.name == "placeAssistantsStep"`); `gamedatas.orders` carries 18 own-perspective rows, never 36. The **initial Port A six and initial Lab six were never observed**, and the history feed's `orderRefresh` does not name the cards that replaced them, so they are not recoverable backwards either. What IS recoverable from a mid-game snapshot is everything static: `tiles` (with explicit `up_left`/`up_right`/`side_left`/`side_right`/`down_left`/`down_right` links, `power_token`, `build_card`) and `achievements`. **Consequence, carried into H3 as a procedure requirement: a snapshot must be taken at table open, before move 1.**

## §1. Where the code goes, and the CLI surface

**Crate split.** `yokohama-bridge` gains a `feed` module: the wire format and its preprocessing, **with no `yokohama-core` dependency** — that keeps the relay binary's dependency surface at `std` + `serde_json` (H0's "NO new third-party dependency" property) and keeps all rules knowledge in one crate. `yokohama-cli` gains a `bga` module (card mapper, setup importer, translator, checkpoint cross-check) depending on both. Nothing about this touches the three fenced crates.

**Command shape:** `yokohama-cli import <capture.ndjson> [--table <id>] [--through <move_id>] [--out <record.json>] [--report <path>] [--answers]`. Dispatch in `main.rs` on `args[1] == "import"` as an exact keyword; every other `args[1]` keeps today's "resume this save" meaning, so the argv contract the guide documents is unchanged. **Justification, one line:** the importer's product is a live-mode `Session` and the setup answers the wizard fills, both of which live in `yokohama-cli`, so an argv keyword adds the entry point without a new binary and without a second place that knows how a `Session` is built.

`--table` disambiguates a capture file holding more than one table (the relay writes per-table, so this is a defensive check, not a routine flag). `--through` bounds the replay at a `move_id` — the honest handle for §0.5's bounded acceptance. `--answers` prints the setup answer sheet and exits without building a `Session`, which is how H1 ships standalone value before H2 exists.

**Record provenance.** The emitted record is a normal live-mode `GameRecord` (`setup_observations` present ⇒ `TrackingMode::Live` on reload, opponent hand hidden). `RunProvenance.run_id = Some("bga-import/<table_id>")`, each `SeatProvenance.controller = "bga-human"` with a `BGA_IMPORT_VERSION` const in `yokohama-cli` and `params` carrying the BGA player id. **No core const is added** — the fence holds. The map §1.5/§1.6 comparison-only fence rides the `run_id` prefix: these records are comparison corpus, never a tuning input.

## §2. H1 — setup importer + vector card mapper

**T1 — the feed reader (`yokohama-bridge::feed`).** Typed parse of the NDJSON: `Capture { received_at_ms, kind, payload }` over `Payload::{Xhr, WebSocket, Snapshot}`, then packet extraction from both transports into one shape — `Packet { table_id, packet_id, move_id: Option<u32>, time, source: History | Socket, notifications: Vec<Notification { uid, kind, log, args }> }`, with `args` left as `serde_json::Value` (the translator owns its interpretation, the reader owns only the envelope). **An unknown `kind`, an unknown `payload.source`, a body that is not the `{status, data:{valid, data:[…]}}` shape, or a socket frame that is not `push.pub.data` is a typed error, never a skip.** A `move_id: null` packet with EMPTY `data` is dropped and counted; the same packet with NON-empty data is an error. Tests: hand-built minimal lines for each arm plus a **redacted slice** of the real corpus committed under `crates/yokohama-bridge/tests/data/` (player ids and display names replaced by stable placeholders; the full corpus stays gitignored and is reached by path).

**T2 — dedupe and supersession (`feed::collapse`).** The preprocessing stage, in this order, each step tested against the real corpus by path plus the committed slice: (a) parse every line; (b) **dedupe on payload identity — the canonical JSON of the packet — never on `received_at_ms`** (ledger N-4: at-least-once delivery over two sockets makes verbatim duplicates normal); (c) **history packets** key on `(table_id, packet_id)` across the four overlapping fetches, and a duplicate key whose content DIFFERS is a STOP; (d) **socket supersession**: walk accepted socket packets in arrival order keeping a running max `move_id`, and on a regression to *m* drop every already-accepted socket packet with `move_id >= m`. **The regression is the operative signal; the `undoRestorePoint` marker is asserted present as corroboration, and a regression with no marker within its packet window is a STOP.** *[Stale as written — H1 fix-wave note, 2026-08-08: the implementation INVERTS this, per inventory §4.1's measurement that a regression-only detector misses 2 of the corpus's 5 real undos (packets 149/170 each superseded one packet with NO `move_id` regression). As shipped in `feed.rs`: the structural `prevpacket` break is the operative signal, the marker is REQUIRED, and a bare regression is its own STOP. Review NOTE-3 re-derived the measurement independently and adjudicated the deviation correct; this note is the plan text catching up.]* (e) **merge**: the history feed is the SPINE (already collapsed, monotone, complete), and a socket packet for the same `move_id` ATTACHES as its enriched form; a disagreement in the notification TYPE SEQUENCE between the two forms of one move is a STOP. Output: `Vec<CollapsedMove { move_id, history: Vec<Notification>, socket: Option<Vec<Notification>> }>` in `move_id` order, plus a `FeedReport` (counts per source, duplicates dropped, packets superseded, moves enriched). Pins: the three real regressions 118→117 / 123→122 / 148→147 collapse exactly; the history spine comes out 194 long with no gaps; the duplicate count is nonzero (anti-vacuity — a dedupe that never deduped is not evidence).

**T3 — the order mapper (`yokohama-cli::bga::orders`).** `OrderVector { req_copper, req_silk, req_tea, req_fish, bonus_vp, bonus_yen, bonus_import, bonus_move, bonus_wh }` → `OrderCardId`, via a table built ONCE from `Rules` with **uniqueness asserted at construction**, so a future card-data change that breaks the key fails a test rather than a live game. BGA's `country` code is checked independently against the matched card's `Country` through a pinned code table carrying its provenance in-source; a disagreement is a hard error even though the vector already matched — a vector hit with a country miss means one of the two data shapes moved. **No match, more than one match, a malformed row, or a country disagreement is a typed error and never a guess.** Fixtures: all 20 corpus rows (expected 20/20), the five design §1 permutation pairs, and the §5 mis-entry cases.

**T4 — the name-keyed identity tables (`yokohama-cli::bga::names`).** Two tables, both checked, both hard-erroring on an unknown key. (a) **Areas**: BGA `tile_id`/`tile_name` → our `AreaType`, needed by both the setup importer and every translator arm that reads `tile_name`; pinned in-source with the corpus as provenance, and asserted TOTAL over our `AreaType` set so a new area cannot be silently unmapped. (b) **Techs**: a `tech_id → TechCardId` **ledger** — a committed JSON with one row per proven identity, each row carrying its evidence (`table_id`, `move_id`, capture timestamp, the observed `tech_name`, `country`, `req_gears`) — seeded with the one row this corpus proves (`tech_id 2 = Mining Technology`). `learn_from(techAcquisition)` appends rows and **hard-errors on a contradiction** with an existing row or with the `(country, req_gears)` corroboration; a lookup miss returns `Unknown(tech_id)`, which is a fact the caller must handle and never a fallback identity. §0.4 is why: a name is the only key BGA gives, and only the socket form of the notification carries the id alongside it, so the table can only accumulate.

**T5 — setup-answer synthesis (`yokohama-cli::bga::setup`).** A `gamedatas` snapshot plus the collapsed feed → a `SetupAnswers` sheet whose every field is `Evidenced(value, provenance) | Absent(reason)`. Filled: `ObservedBoard.tiles`/`sites`/`tokens` from `gamedatas.tiles`; `achievements` from `gamedatas.achievements` by `(class, qty_1, qty_2, bonus_1_vps, bonus_2_vps)` vector match against our `AchievementType` set (same discipline as T3 — ambiguity is an error); `port_a`/`port_b` from the port-located `orders` rows through T3; `lab_a`/`lab_b` from the lab-located `techs` rows through T4, `Absent` the moment any one id is `Unknown`; per-seat `StartingOrderChoice`, which the corpus settles as **`Unknown` for BOTH seats** — there is exactly one `orderDiscarded` per player (moves 2 and 3 here), it names the DISCARDED card in full and says nothing about the kept one, so the starting order becomes known only when it is later completed and arrives as a `RevealStartingOrder` event on the translator's path, which is precisely what the live-tracking machinery already models. The two discarded rows (here BGA 24 → O03 and BGA 25 → O27) are known identities and belong in `orders_removed`; T5 asserts that placement rather than dropping them. **The board geometry is derived, not assumed:** BGA's tile links are walked into our row-major `board_gen::row_lengths` order, and **BGA's adjacency is then cross-checked against our staggered pyramid — a mismatch is a STOP.** That check is free and it is a differential of our board topology against an independent implementation, which is the honesty dividend pointed at setup rather than at scoring. `location` and `country` code enums are DECODED from the corpus and pinned with provenance; an unrecognized code is an error (§0.5 leaves open whether order `location: 1` is the deck or the box — T5 settles it from evidence or records it as undetermined; it must not be guessed, because if it is the deck then the initial Port six may be recoverable after all and §0.5's bound loosens).

**T6 — the `import` entry point and the guide (H1 closes here).** `main.rs` keyword dispatch, argument parsing with typed errors, `--answers` printing the sheet (every `Absent` field naming its reason, so the human knows exactly what the wizard will still ask), and — where the sheet is complete enough — construction of a live-mode `Session` through `Session::new_live` with the synthesized `SetupObservations` and choices. **The bridge answers the wizard's questions; it never bypasses the engine, and it never answers a question it lacks evidence for.** Guide pair updated in the same commit; `guide_sync` green.

## §3. H2 — catch-up translator and the acceptance replay

**T7 — the translation census (measurement BEFORE the translator).** For each of the 194 collapsed moves, classify its notification tuple by what it determines on its own — `Determined` (the tuple names one engine `Move`), `EngineFiltered` (the tuple plus `get_legal_moves` leaves one), `Underdetermined` (needs the evidence ladder below), `SocketOnly` (determined in the enriched form, underdetermined in the stripped one) — and commit the result as `docs/plans/2026-08-XX-bga-translation-census.md`. **This is a source-side census and needs no replayed state**, which is what makes it runnable before T8 exists. It asserts that every move is classified and that no class is empty by accident; **it asserts no threshold and no direction** — its job is to size H2 honestly and to tell the orchestrator, before any translator is written, how much of the acceptance run the stripped history can carry. The evidence ladder it evaluates, in order: the notification's own args → the engine's legal list → the `log` string parsed **only through a pinned template table** (the templates are stable strings; a template that does not match a pinned entry is a STOP, never a regex guess) → corroborating later notifications in the same move (`payForPres` names fee amounts, recipients and the tile, which fixes a route's fee vector; `resourceChange`'s rendered gain fixes an area action's yield) → the next `counters` reading.

**T8 — the translator (`yokohama-cli::bga::translate`).** A state machine over `CollapsedMove`s producing, per move, an ordered `Vec<PlannedEvent>` where each is an engine `Move` or a `RecordedEvent` reveal (`RevealOrders`/`RevealTechs`/`RevealStartingOrder` — port and lab refills are reveals, exactly as typed live entry treats them), together with the notifications that justify it and its census class. **Every planned event is applied through `Session::apply`, the same checked `apply_move` boundary as typed entry** — the translator proposes, the engine disposes. The turn's phase machine is the engine's, not a re-implementation: the translator consumes notifications against `get_legal_moves` at the head of the queue, so queued choices (any-good picks, warehouse takes, movement-icon assistant moves, church/customs space, Station placement) resolve as themselves. An `Ambiguous` outcome names every surviving candidate and STOPS. Pins per arm, each built from a real corpus move cited by `move_id`.

**T9 — the checkpoint cross-check (`yokohama-cli::bga::checkpoint`).** BGA `counters` versus engine state, at three densities: **dense** on every socket packet carrying `counters` (moves 107..194), **anchored** at the three `gamedatas` snapshots, and **terminal** at `finalScoring`. The counter→engine-field conversion is itself a checked artifact — `copper/silk/tea/fish`, `yens`, `imports`, `gears`, `vps`, `flags_*` per country, `board_assists/hand_assists/wh_assists`, `board_president/hand_president`, `board_shops/houses` and their warehouse twins, `orders_done`, `orders_hand`, `tech_count` — and **an unmapped counter key is an error, never ignored**; a key we deliberately do not model is listed explicitly with its reason. A mismatch is a STOP with a field-level diff naming the move, the counter, BGA's value and ours. The terminal check is the honesty dividend: our final scoring against BGA's, per player, per category.

**T10 — the acceptance run and its report.** Run the bounded replay of table **895724349** end to end, emit the record, verify it with `replay_strict`, and write `docs/plans/2026-08-XX-bga-acceptance-895724349.md`: how far the replay reached, what stopped it if anything did, the census table, every checkpoint result, and the final-score comparison. **The report states the bound honestly** — §0.5 means a move-1 replay of THIS corpus is only possible if T5 recovers the initial Port/Lab, and if it does not, the run is a bounded replay from the first checkpoint the evidence supports, which is a real result and not a failure. Ledger row and carry-forwards updated with it.

## §4. STOP conditions, verbatim

These are quoted as they stand in the governing documents and the task brief, and they are copied verbatim into every task brief this plan generates.

- From design §2.3: **"A translation the engine refuses is a STOP with a state diff — never a skip."**
- From the standing brief: **"If a captured-game replay diverges in a way that implicates ENGINE RULES (engine refuses a move BGA allowed, or scores differently), that is a STOP-AND-DOCUMENT with a full state diff — an owner-gated rules question per the repo's exposure map — NEVER an engine edit and NEVER a translator hack that fakes agreement. Hard-error-never-guess is the bridge's standing posture."**
- From design §6: **"the bridge pins itself to the data shapes captured in H0 and hard-errors on surprises (never guesses); a drift is a maintenance task, not silent corruption."**
- From the ledger's fences: **"no changes to `yokohama-core`, `yokohama-oracle`, `yokohama-difftest`. `SEMANTICS_REV` unmoved."** A core diff is a STOP.

A STOP means: the run halts at that move, the diff is written to the report, the ledger gains a row, and the question goes to the owner. It does not mean a `--force`, a skip flag, a widened acceptance, or a translator that shrugs.

## §7. Task order rationale and risks

T1→T2 before anything engine-facing because every later task reads a collapsed feed and a translator built on an uncollapsed one would encode duplicates as real moves. T3/T4 before T5 because setup synthesis is card identification applied to a snapshot. T6 closes H1 as something that ships value alone (the answer sheet) even if H2 runs long. **T7 strictly before T8** — the census is the measurement that decides how much of the acceptance run stripped history can carry, and writing the translator first would mean discovering that by debugging. T9 can land before or after T8's last arms, but its conversion table must exist before the first STOP is adjudicated, or a divergence has no diff to show.

**Named risks.** (1) **§0.5's bound** — the likeliest honest outcome is a bounded acceptance replay rather than a move-1 one; the mitigation is that it is a STATED bound with a fixed H3 procedure, not a silently truncated run. (2) **§0.1's asymmetry** — history is log-shaped, so a class of moves may be genuinely underdetermined; T7 measures the size of that class before T8 pays for it. (3) **§0.4's tech ledger** — 29 unknown ids mean `--answers` will report `Absent` lab slots on most imports until a socket-covered game fills them; the wizard asking a human for six tech names is the designed fallback, and it is not a defect. (4) **BGA schema drift** — every table in T3/T4/T5 carries provenance in-source and hard-errors on an unrecognized code, which turns drift into a failing test rather than a corrupt record.
