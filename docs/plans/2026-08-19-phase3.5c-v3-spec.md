## 4. The L2 instrument and the incremental-value rule (cycle steps 1 and 3)

### 4.1 The instrument (new; probe-side only; nothing moves `Feature::ALL` at this step)

Two additions to `eval_probe`, both instrument tasks under the data-contact rule:

1. **The `terminal_margin_now` candidate column** — ninth `CandidateColumn` variant,
   registered in `CANDIDATE_COLUMNS`, token == name, reachable-from-argv pin extended,
   behaviour pins per §2. Nothing in `score` calls it.
2. **Extended score tables — the "17th column" L2 machinery** (round 3 named this as V3's
   measuring tool). Grammar extension to `--score-table`:
   `<name>=<base>[+<column>=<e>/<l>]…` where `<base>` is `v1 | v2 | v2-draft |
   <16 i64>/<16 i64>` and each `+` clause names a candidate column with an early/late
   weight pair. **Parse rule (review SHOULD-4):** extension clauses are stripped greedily
   from the RIGHT while the suffix matches `+<known column token>=<i64>/<i64>`; what
   remains is the base. A vector-form base documents that its entries use bare or
   `-`-signed integers (a leading-`+` entry is refused with a typed error naming the
   ambiguity) so a stray `+` can never silently re-segment a spec. Evaluation:
   `candidate_total`'s mirror loop plus, per extension clause, the interpolated weight
   times (viewer's column value − the opponent-extreme rule applied to the column),
   exactly as a feature would be priced — so an extension table IS the admission's
   arithmetic preview. Refusals name what was seen; an extension clause naming an unknown
   column is an error; the base-vector width stays keyed to `Feature::COUNT`.

### 4.2 The L2 reading (pre-registered before the corpus runs)

4a} with FLAT (e, l) = (r, r) pairs — stage-shaping is the post-L2 hand-set step, informed
by the flat term's per-stage reads. **The anchor rule is pre-committed here (review
