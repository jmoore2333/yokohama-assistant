## 7. F's brainstorm items (owner and orchestrator, before F's spec)

1. **Turnstile — where.** At the multiplayer button (the widget renders on the click, its token rides `/enter` or the first API call) or on the whole door (a widget script on every door load — which must NOT reach the offline door or the precached shell: E's `/shell.bin` lesson is that anything the edge injects or the door fetches at load time is a liability). The button is the candidate.
2. **Turnstile — cost and metering.** Turnstile is free; its server-side verify is a subrequest from the Worker on an ALREADY metered path (`/enter`, `create`, `join`), never a new invocation on the door. On the NAS the verify would need the secret and outbound network from axum — or Turnstile is the Worker host's alone, since the NAS sits behind Access.
3. **Turnstile — against what.** Today the hostname-wide Access door stops anonymous traffic before any Worker runs; Bot Fight Mode challenges bot-shaped requests; the rate-limit rule bounds the oracles. Turnstile matters for the PUBLIC-door end state (state 2: the door and the shell public, the API behind Access) — decide whether it is a state-2 precondition (the lane document §8's list) rather than a change to today's door.
4. **The wording path.** Keep the notice, blurb and link as build values (a change = a rebuild and a deploy, delivered by F-1's door), or move them to a static `site.json` (an asset-only deploy) — the owner's call on how often the footer might change.
5. **The NAS marker.** Whether the self-host's sweep and delete leave a marker sentence like the Worker's ("this table expired on … after 90 days without activity") or keep today's "no such game".
6. **The sweep's cadence and its first run.** Hourly; on a host that has been running for months, the first sweep with a TTL set would end every idle table at once — a dry-run listing (`--sweep-dry-run` or a log line per table before the first deletion) is worth a rule.
