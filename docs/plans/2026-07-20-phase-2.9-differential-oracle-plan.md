# Phase 2.9 — Differential-testing harness + deep verification (pre-Phase-3 gate)

**Status:** QUEUED. Executes AFTER PR #2 (`engine-authority`) merges to master, BEFORE the Phase-3 computer-player spec. Owner-approved 2026-07-20; improvements folded in by the orchestrating session that ran the engine-authority phase.

**Why this phase exists (the one-paragraph case):** every gate this project runs proves *self-consistency* — the engine agreeing with itself. The engine-completion final review found four Critical rules bugs (per-assistant fees, one-tech-per-title, the TH power gate, unwired VP bonuses) that 15,000 fuzz games structurally could not see, because enumeration and application shared the same wrong belief. Differential testing against an independently-authored oracle is the only tool class aimed at shared-wrong-belief bugs — this engine's documented failure mode. And Phase 3's first mandated task (the factored/lazy action interface, guidingpath Phase-3 handover) is a rewrite of exactly how legal moves are delivered: that refactor must run against this harness, not against self-consistency fuzzing that grades its own work. The harness is the guardrail Phase 3 runs inside, not a detour before it.

**Execution model:** run as an **ultracode workflow** (owner's standing opt-in for this phase). Three orchestration constraints are binding:

1. **Stage gates are sequential decision points.** Do not fan out all six stages at once. Land Stage 1, review it, reassess scope; then Stage 2; then decide how much of 3–6 the findings justify. Fan-out is WITHIN a stage (parallel oracle-module authors, parallel divergence verifiers), never across ungated stages.
2. **The independence rule is enforced by prompt construction + attestation.** Reference-authoring agents receive rules sources only and are instructed never to open the engine files named below; implementation-reading agents never author oracle logic. Every agent's report attests which files it read. The final report includes the attestation table.
3. **Divergences get adversarial verification before triage.** Every claimed divergence is independently reproduced (fresh agent, minimal repro) before it enters the three-way+one triage. Fewer, proven, with evidence.

### THE INDEPENDENCE RULE — read this twice

Every reference implementation MUST be authored from the rules sources, NOT from the existing engine code:

- `analysis-1/yokohama-kb/01-rules-reference.md`
- the rulebook PDF in `analysis-1/`
- `analysis-1/yokohama-kb/07..09-*.yaml` (card/site data)
- `guidingpath.md`'s decision log (the rulings that resolve rulebook ambiguity)
- CLAUDE.md's "Rules knowledge" section

An agent writing a reference implementation **must not read** `legal_moves.rs`, `apply_move.rs`, `movement.rs`, or `scoring.rs`. Use separate agents for authoring-the-reference and reading-the-implementation, and the report states which agents saw which files. A reference derived from the implementation agrees by construction and is worth nothing.

**Honesty caveat (what "independence" can mean here):** the KB and the decision log were themselves corrected by engine-era findings — the achievable bar is independence from *engine code*, not from project history. That bar is still valuable (a fresh reading catches transcription-level divergence and unexamined assumptions); the report must not claim more than it.

Where reference and implementation disagree, **adjudicate against the rulebook** — never "fix" the reference to match the engine, and never weaken the engine to match the reference, without a rules citation.

### Structure

Put the oracle in a **new dev-only crate** (`crates/yokohama-oracle`), not in `yokohama-core`'s tests. Rationale: any coupling to engine internals is visible in `Cargo.toml`, so nobody can quietly refactor the reference to share engine helpers and destroy its independence. The oracle depends on `yokohama-core` only for *types*, never for logic — **and every stage's review explicitly re-checks the oracle crate's `Cargo.toml` + imports for the types-only rule.** That check is the visible-coupling guarantee actually doing its job.

The board is small — 10 areas (2p, 2×5), 14 (3p, 2×7), 18 (4p, 3×6) — so brute-force enumeration is genuinely tractable. Exploit that. The oracle does not need to be fast or elegant; it needs to be *legible against the rulebook*.

### Staged deliverables

Land each stage as its own gated, reviewed commit. Do not attempt all of it in one pass.

**Stage 1 — legal-move oracle (highest value, and the big rock).** A declarative, brute-force enumerator of legal moves written from the rules. **Driver shape, pinned:** the ENGINE drives seeded self-play and applies moves; the oracle only *enumerates per state* and the runner compares the two sets — the oracle needs no independent `apply`. Report both directions separately: moves the engine offers that the oracle doesn't (**soundness**) and moves the oracle finds that the engine misses (**completeness**). Consequence for the coverage map: the harness checks enumeration on engine-reachable states only — say so. Completeness failures matter most for Phase 3: a bot searching an incomplete action space looks *dumb* rather than making the engine look *wrong*, which is near-undebuggable once learning is involved. Scope note: this stage must model the full turn machine, techs, and the choice queue to be comparable at all — it is the largest single work item in the phase; the stage gate exists so an overrun triggers a scope conversation, not a silent quality collapse.

**Stage 2 — scoring oracle (cheap, do immediately after 1).** Independent implementation of final scoring and the ranking/tie-break, from the rules reference. Compare `final_result` on terminal states over large N. This is the bot's learning signal; if terminal utility is wrong the bot optimizes the wrong objective. (History: the tie-break's only test was vacuous until 2026-07-20.)

**Stage 3 — movement/route oracle.** Brute-force path enumeration on the real boards vs. the affordability-pruned DFS, comparing the destination/cost/credit-vector label sets. The implementation's pruning soundness rests on a monotonicity argument that has been reasoned about (twice, by reviewers) but never differentially tested.

**Stage 4 — property/metamorphic suite for `apply_move`.** Differential testing doesn't apply (the implementation is its own oracle), so use invariants instead: conservation laws, replay determinism and idempotence, `check_invariants` clean after every arm, and a systematic sweep asking of EVERY raw arm — *does this arm self-defend against out-of-range/ill-formed payloads, or does it panic?* One arm (`apply_build_shophouse`) was found missing that guard by accident; nobody has swept the rest.

**Stage 5 — mutation-test the invariant suite itself.** For each invariant in `invariants.rs`, a state that violates it must be caught. **Extend, don't rebuild:** the T18 fuzz scaffold already carries nine corrupt-state tests proving invariants fire — inventory those first, then sweep for *uncovered* invariants (the external review's I-7 named BoardLayout adjacency/canal/site keys and structural symmetry as unchecked). An invariant that never fires is not protection.

**Stage 6 — targeted deep audit** of what remains, per the method requirements. Timeboxed; the stage gate after 5 decides its scope from what 1–5 found.

**Close-out — stamp semantics rev 1.** When the campaign converges, land the semantic rules-revision stamp (mandatory Phase-3 handover item: a revision identifier that MUST change for every behavior-affecting engine modification, ideally CI-enforced, plus a terminal-state digest in `GameRecord` verified on strict replay — see the guidingpath handover item for the full shape, and `record_stats` switches to `replay_strict` closing I5). The moment the differential campaign passes is the defensible birthday for "rev 1"; the training-data guard exists before any corpus does.

### Method requirements (these produced the best findings this project has had)

- **Census over enumeration, not inspection.** Enumerate the exhaustive set (every field, variant, arm, branch), then *drive N games and measure* which members are never exercised. "I read it and it looked fine" is not a finding or a clean verdict.
- **Executed evidence beats reasoning.** Build scratch probe crates *outside* the repo. Paste real output.
- **Adversarial fixture construction.** Where a bound is claimed, construct the worst case and check the analytic bound too.
- **Mutation to prove teeth.** Any test claimed as coverage must be shown to FAIL when the code it covers is broken. Several existing tests passed while covering nothing.
- **Every CLEAN verdict says how it was established** — "traced X, holds because Y." Silence is not a clean verdict.
- **An explicit NOT-COVERED section.** A known gap is manageable; an unknown one is not.
- **Beware "the fuzzer never hit it."** Uniform-random self-play systematically under-samples — this repo has documented one case (I6: a published branching baseline was an artifact of the measurement policy) and another (a defect unreached in 3,800 random games but ordinary at a table). A claim of unreachability is argued from the *rules*, not from a census miss.

### Divergence triage — four-way

Every verified divergence resolves to exactly one of:

1. **Engine bug** — fix, with a failing test first.
2. **Oracle bug** — fix the oracle, and say what misreading caused it (that misreading is itself signal the rules text is hard).
3. **Encoding divergence** — the choice queue, singleton auto-resolve, canonical-path representatives, `Skip`, and the reveal/record machinery are *engine encodings* the rulebook doesn't have. For these, the **decision log is normative for encoding; the rulebook for rules.** A mismatch in how the oracle mapped rules to the engine's move/choice vocabulary is fixed on the oracle side against the decision log — it is NOT a rules ambiguity and must not pollute the ruling list.
4. **Genuine rules ambiguity** — neither source settles it. **Do not guess and do not pick one.** Collect for the owner with: the exact rules text, both readings, which game situations distinguish them, and what each implies for play. This is the highest-value output of the phase — an unstated assumption baked into a bot's training is invisible later.

### Reproducibility (non-negotiable for a harness)

Every divergence is reported as a **minimal reproduction**: seed, player count, and the shortest move prefix that reaches the diverging state. Implement shrinking — a 900-move repro nobody can act on is barely better than no repro. This is what makes the harness usable a year from now.

### What NOT to do

- Do not weaken, delete, or `#[ignore]` an existing test to make a sweep pass.
- Do not "fix" a divergence by changing whichever side is easier.
- Do not report unverified findings. Fewer, proven, with evidence.
- Do not touch the CLI beyond what the harness needs — CLI work belongs to the pre-gate checklist (its own track).
- Do not treat this as a review that ends in a report. **The deliverable is running code that keeps catching regressions through all of Phase 3.**
