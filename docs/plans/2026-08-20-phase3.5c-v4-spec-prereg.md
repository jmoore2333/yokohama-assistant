One owner per quantity along `placement → enabled action → produced asset → fulfillment →

the chain advances — credit neither disappears nor persists twice.

|---|---|---|---|
| Assistant presence (where) | S | `ProductionAccess`, `TrackAccess`, `AssistantAreasDistinct`, `PresidentAdjacentAssistants` | recovery → hand-core/excess (V2's ordering stands, §5 family 8) |
| Enabled-action potential | S | the access features at REALIZABLE power | the action's produced asset (E-resource stocks, track presence in the mirrors) |

| Trade goods (stock) | E-resource | `TradeGoodsStock` | consumed at fulfillment (stock drops; the order's realized value lands) |
| Realized fees | E-resource | land IN money; never a separate cumulative asset | — |

## 5. The feasibility benchmark: pairs, margins, collateral (checkpoint §5, instantiated)

### 5.1 Conventions (fixed here, before any pair is built)

- A PAIR is two constructed legal positions (fixture-built states rendered to views;
  `Rules::standard()`; scenario-suite construction precedent) with a declared DIRECTION
  (`value(A) > value(B)` for the named seat), a declared STAGE (`p = 0` or
  `p = PROGRESS_FULL_PPM` — endpoint-exact under `interpolate`, so every pair is exactly
  linear in the integer weight vectors; mixed-stage tension is covered by registering pairs at
  both endpoints where both matter), and a declared MARGIN. **Both fixture sides must REALIZE
  the declared stage** (`progress_ppm` printed by the fixture and equal on both sides and to
  the declaration — early pairs on fresh-clock boards, late pairs with a saturated clock);
  a mismatch is a fixture defect, not a reading.
- **Margin convention:** margins are declared in VP UNITS and convert to score units through
  the candidate table's own interpolated `VictoryPoints` weight at the pair's stage
  (`margin_score = margin_vp · w_vp(stage)`), so "one good turn ≈ a majority bonus" style
  rules arithmetic transfers to any table under test. A pair without a rules/VP-justified
  margin is DIRECTION-ONLY (`margin_score = 1`, the smallest integer separation) — the
  checkpoint's rule verbatim.
- **Collateral:** where legality forces co-movement (a goods change also moves order distance
  and achievement progress), the fixture mechanically PRINTS its full 27-feature delta and
  the pair's registration lists the expected nonzero collateral rows; an unlisted nonzero
  row at run time is a fixture defect (stop, fix, re-freeze that fixture — before results,
  this is sanctioned; after, it is a new counted item).
- Every pair is registered as `(id, family, seat, stage, direction, margin_vp | direction-only,
  collateral list, construction recipe)`. The FROZEN pair list is the §7 step-2 package; this
  spec fixes the families' contents and each family's minimum pair count; exact fixture code
  lands red-first at step 2.

### 5.3 Part A — the collision test (weight-free)

**Vector definition (fixed):** a position's signature for collision purposes is the
DIFFERENCED complete feature vector `(v_f(me) − v_f(opp*))` over all 27 features at the
position's progress bucket — the exact input every possible table scores, so signature
equality implies score equality under EVERY table (the unrepairable-by-weights reading is
literal). Signatures are computed by the probe columns (step 3) over: every §5.2 pair side,
and the exhibit-class roots' candidate SUCCESSOR sets (g1-e113's 139 placements; the §8
development roots' root tables).

**Blocking rule (checkpoint §5 verbatim, operationalized):** a collision BLOCKS iff its
equivalence class contains a REGISTERED value-distinct pair (every §5.2 pair is registered
value-distinct by construction). Organic successor-set collisions at the roots are REPORTED
as diagnostics with their class sizes (the e113 36-way top tie's complete-vector fate is a
step-4 MEASUREMENT, never assumed). Zero blocking collisions on the frozen pair set is the
necessary condition; an unrepairable blocking collision closes the milestone at the §7 step-4
fork.

### 5.4 Part B — the bounded compatibility solve

**The arithmetic model (the SHIPPED table's actual arithmetic, checkpoint §5B):** integer
weights per feature per stage vector, box |w| ≤ 64 (V2's max magnitude is 40; the box is the
declared no-saturation/plausible-scale bound), evaluation through the exact production
arithmetic — endpoint stages make every registered pair an exact LINEAR integer inequality
`Σ_f w_f(stage) · Δv_f(pair) ≥ margin_score(pair)` in the 27-dim stage vector (54 integer
variables across both stages; pairs couple stages only through the margin convention's
`w_vp(stage)` self-reference, which is linear too since margin_score = margin_vp · w_vp moves
to the left-hand side). Two standing constraints ride every solve: `w_vp ≥ 1` in BOTH stage
