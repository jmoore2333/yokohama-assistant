# Phase 3 Map — the computer-player ladder

**Date:** 2026-07-25 · **Status:** brainstorm output, all sections approved in-session (Jeremy + Claude, 2026-07-25); this written form awaiting Jeremy's review — **provisional by design**; expected to be amended as sub-phases land. This document supersedes `guidingpath.md`'s one-paragraph Phase-3 ladder once Jeremy accepts the guidingpath update proposed in §10.

**What this document is:** the broader Phase 3 map — sub-phases 3.0–3.5 plus the above-bar band, what each is for, and what each must prove before the next begins. Each sub-phase later gets its own full **spec → plan → TDD execution** pass; this map's job is to make those cheap to write and to keep us out of corners. It deliberately does **not** specify any sub-phase.

**What this document is not:** an implementation spec, an algorithm commitment, or authorization to skip a gate.

---

## 1. Settled inputs (owner direction, not up for re-litigation by sub-phase specs)

1. **Honest from day one.** The first usable bot acts only on information available to its seat. Full-state visibility survives only as an explicitly labeled diagnostic, or (if research supports it) as privileged training-only teacher/critic information whose deployed student provably cannot access it.
2. **Two-player strength milestone first.** Observation, utility, arena, and search interfaces stay extensible to 3–4P; actual 3–4P strength work lives above the bar.
3. **Compute envelope discovered, not imposed** — and never a cut line. Resource ladder: M5 MacBook Air 24 GB (development) → 96 GB workstation (larger trees/corpora/search state) → cloud (offline sweeps). Moving up a tier is an acceleration, not a directional change; architecture selection must not be biased by laptop constraints. Optimization can always come later.
4. **Success evidence is method-specific**; thresholds derive from measured variance, never preset N or arbitrary percentages.
5. **No external corpus exists** (verified: no Yokohama bot, replay corpus, or opening book anywhere). Self-play and constructed scenarios are the source of experience.
6. **Grown from its own corpus.** Evaluator features come from rules structure, measured self-play, and scenario iteration — not from human strategy priors. Human-game benchmarking is a late, optional, comparison-only activity, never a training input.
7. **Neural nets are out of Phase 3.** The ladder is not built around them. The ladder's own instrumentation (corpus scale, generation throughput, evaluator insight, strength curves) is collected as a by-product and becomes the dossier that would make the NN question answerable in some future session.
8. **Practical ceiling: MCTS-variant territory.** "Strongest non-neural player" is a higher bar than this project needs to chase.
9. **The milestone bar** ("provably plays to win", 2P) requires **all four**: a constructed-scenario suite · statistical superiority over preserved rungs (paired seeds, seat swaps, CIs) · decision explanations for every chosen move · owner acceptance play through the CLI. The evaluator is a material, *progressing* part of this — versioned, re-proven each time.
10. **LLM-as-teacher is a standing tool, not a rung**: frontier models assist with weighting design, sampling sanity, and degenerate-loop detection (e.g. retreat cycling); they are not a strategy oracle inside the player.

## 3. Frame and principles

**Two-resolution map.** Below the bar: six sharp sub-phases (3.0–3.5), each one spec → plan → TDD pass with an executable gate the next waits on. Above the bar: a coarse, evidence-gated band (3.6+) with an explicit stopping rule. Sharp where we know things; honest about guesswork above.

**Threads, not boxes** — five things cross sub-phases rather than living in one:

| Thread | Behavior |
|---|---|
| Evaluator | Versioned (v1, v2, …); every version re-proven in the arena; progresses as long as the ladder does |
| Scenario suite | Grows every sub-phase; a scenario that catches a regression is never deleted |
| Honesty invariants | Leakage + conservation tests run against every policy that exists, not once at 3.0 |
| Preserved rungs | Every bot that passes a gate stays alive as an arena regression opponent |
| Explanations | From the first evaluator on, every chosen move traceable to the terms responsible |

**Hard sequencing (load-bearing structure):**

1. **3.0 before any bot that consumes state** — honest-from-day-one makes the observation boundary the first artifact, not a retrofit.
2. **3.1 before any search built over actions** — mandatory handover item; the checked-apply cost problem lives here.
3. **3.2 before any strength claim** — no bot is called stronger than another without the paired arena.
4. **3.4 before committing the serious-search architecture** — the two external research reports picked incompatible first algorithms; a cheap local experiment decides, not literature.

**Deliberately soft (guesses we'll revise):** the evaluator feature set; the depth-semantics choice (settled empirically in 3.3); above-bar rung order; where flattening lands.

**The live-gate dependency floats.** Phase-2's physical-game gate must be *played and dispositioned* before the bar is declared (3.5's gate), but it attaches to the calendar, not to a sub-phase: if the table game happens during 3.1, the dependency dissolves early. 3.0–3.4 are gate-independent by ruling (`guidingpath.md` headline).

**Two-player posture.** Every strength gate is 2P. Interfaces are typed over N seats from 3.0. The family-weighted policy is still exercised at 3–4P from 3.2 on — by the fuzzer, its other mandated consumer.

## 4. Execution model

Each sub-phase runs: **spec → plan → TDD execute → PR with detailed documentation → dynamic-workflow review → merge → next sub-phase.**

- **Review workflow (owner-directed):** a Workflow orchestration fans out the pr-review-toolkit agent suite over the PR, collects reports, then an **Opus 5 adjudicating reviewer** synthesizes verdicts; the orchestrator consumes the verdict and applies fixes under the receiving-code-review discipline (verify, don't blindly apply). Reviewers post findings *and resolutions* as **PR comments as they go** — the audit trail that makes every merge a documented, revisitable fork point.
- **Model dispatch (owner-directed 2026-07-25):** Fable is the overall orchestrator and runs the plan-development agents; **Opus 5 is the default for development execution and review agents** (sufficient for most of that work); **Sonnet 5 agents are permitted for the PR-review fan-out provided an Opus 5 reviewer adjudicates** their collected findings; clean-eyes verification agents (the pass-through check) run at Opus 5 or above. Escalate a tier only where capability changes outcomes.
- **PRs merge to master when properly reviewed** — no per-merge owner pause.
- **Merged branches are preserved.** Branch deletion is never autonomous; it is a joint task with Jeremy. Together with the comment trail, this keeps "go back in time and pick another path" a real (if expensive) operation.
- **Autonomy envelope:** this accepted map is the authorization envelope for an independently-operating window across **3.0–3.4**. Within it, the orchestrator may move through gates — rules rulings, `SEMANTICS_REV` bumps, `guidingpath.md` updates — **without stopping** when highly confident, research-backed, and **independently verified by a clean-eyes subagent**; each pass-through is recorded as it lands. `SEMANTICS_REV` bumps are expected, not exceptional (at least one is anticipated), and are not blocking by themselves; same for guidingpath updates carrying key changes, so long as the larger direction is not radically changed.
- **Hard stops (owner-only):** radical direction changes; genuinely table-dependent rules ambiguity; the 3.5 owner acceptance play; branch deletion. 3.5 is owner-in-the-loop by construction.
- **Oracle co-evolution rule:** any engine-touching sub-phase carries an oracle-impact assessment. Oracle-side changes are authored under the ORACLE INDEPENDENCE RULE (rules sources only; types-only dependency; implementation-aware agents never author oracle rules logic) so differential testing keeps its meaning rather than becoming a second set of tests around the engine's own beliefs.
- **Repo gates unchanged:** per-edit debug suites + clippy after every task; the eight release-tier gates before every merge (the seven pre-Phase-3 gates plus the Phase-3.0 observation-honesty sweep, added within 3.0's authority — this bars skipping a gate, not adding one); TDD throughout; dated docs in `docs/plans/`.

Honesty machinery as standing tests: counterfactual-leakage invariance (decision distribution unmoved when inaccessible details vary under fixed observation + sampler seed) and sampler conservation. Omniscient access survives only as a labeled diagnostic.

### 3.2 — Arena, rungs, and the weighted policy
**Purpose:** make strength claims possible; pay the fuzzer promise (`guidingpath.md:170`).

**Preserved rungs at close:** uniform; retreat-averse (bracketing extremes, kept deliberately); family-weighted.

**Exposure:** none rules-level.

### 3.3 — Evaluator v1, shallow search, scenario suite
**Purpose:** the first purposeful bot; the instrument that makes feature/depth/throughput facts cheap.
**Contents:** evaluator v1 typed over `PlayerView` only (honesty by construction), transparent hand-set weights over features grown from rules structure + measured self-play (country-set progress, order economics, board presence, track positions, achievement races, end-trigger proximity). Greedy rung, then shallow search over **completed player hand-offs**; the depth-semantics choice (turn-boundary vs atomic-with-quiescence) is settled here empirically. Hidden information via the simplest honest scheme — sample K worlds from the 3.0 sampler, aggregate — with the deeper comparison deferred to 3.4. Scenario suite v1 as executable fixtures over constructed states (PR #5's `pub place_setup_dummies` is a Phase-3 primitive for this). Explanations land day-one; with them, CLI `suggest my move`. The **Opus play-tester** (Forge MCP: an Opus agent reads the rules and plays the CLI against the bot in a real PTY) may first fire here — a qualitative probe whose impressions can be checked against the bot's stated reasoning; not a gate ingredient.
**Gate:** beats family-weighted random with honest intervals (paired, seat-rotated); scenario suite v1 green; every chosen move explainable; leakage invariants green against the new bot. Preserved as a rung.
**Starting-order note:** the player interface covers the `finalize_setup` Keep decision from 3.2's arena on (random at first); from 3.3 it becomes evaluator-informed.

### 3.4 — The discriminating experiment
**Purpose:** choose the serious-strength architecture with local evidence — the question the two research reports answered incompatibly (RIS-MCTS-first vs evaluator/alpha-beta-first).
**Contents:** matched-budget 2P comparison of (a) 3.3's determinized shallow search, budget-scaled; (b) UCT-family MCTS with family-weighted proposals + progressive widening sized from measured distributions; (c) information-set variants — re-determinization considered only if determinization's pathologies (strategy fusion, non-locality) are *measured* to matter here, not assumed from Hanabi. The bounded **treant build-vs-adapt spike** lives here; adoption on merit only. Report strength-per-node *and* strength-per-wallclock (they can rank differently). Hardware limits do not select the architecture (§1.3).
**Gate:** a written, data-backed architecture decision (decision-log row + ADR-style record) including the evidence that would reverse it. The last cheap moment to be wrong about the architecture.
**Exposure:** none (pure compute).

### 3.5 — The bar
**Purpose:** assemble and prove.
**Contents:** the chosen architecture productionized; evaluator v2 (informed by 3.3/3.4 ablations — feature interactions respected, no monotone-ablation dogma); opponent-denial and end-timing depth; tuning within the *discovered* compute envelope, escalating tiers freely (§1.3).

## 6. Above the bar: the band (3.6+)

**Coarse by design; ceiling: MCTS-variant territory.** Every rung follows one contract: **entry evidence** (a measured reason to build it) → **gate** (beats its parent at matched compute, both axes) → **preservation** (joins the rung ladder).

Candidate rungs (order provisional):
- **Deepen the chosen architecture** — budget scaling, observation-aware tree reuse, transpositions; perf cards (§8) played as measurements demand.
- **Imperfect-info depth** — ISMCTS / re-determinization, entered only if exploitation probes show determinization actually leaking; 3.4's losing candidate may re-enter here if evidence changes.
- **Opponent modeling** — 2P exploit/respond from public move history.
- **3–4P honesty and strength** — the multiplayer backup-model decision (MaxN-vector vs paranoid vs best-reply vs policy opponents) deliberately lives here; mechanics are warm via the fuzzer's 3–4P use of the weighted policy.
- **Optional: human-game comparison** — comparison-only benchmark, never training input.

**Stopping rule:** when a rung fails to beat its parent at matched compute, confirmed once more at a higher budget, the ladder top is declared. The accumulated dossier (corpus scale, generation throughput, evaluator insight, strength curves) is the input to any future NN reconsideration — a different session's decision, not this map's.

## 11. Revision protocol

This map is provisional by design. Amendments happen at sub-phase closes (or when evidence demands), under the execution model's rules: confident + clean-eyes-verified changes proceed and are recorded; radical direction changes stop for Jeremy. The map document itself is the envelope of the autonomous window — when a sub-phase spec wants something outside its mapped purpose or gate, that is the signal to stop and re-map.
