## 4. The architecture and the standing rules

- **`crates/yokohama-web` + `crates/yokohama-wasm` + `crates/yokohama-worker` + `web/` + `worker/` — the browser lane** (merged to master 2026-09-11; the M6 "room" charter is `docs/plans/2026-09-14-web-frontend-m6-room-plan.md`, whose §3 is what stays fixed through every cycle, and the M6.5 hosting umbrella is `docs/plans/2026-09-19-web-frontend-m6.5-hosting-spec.md`; each cycle's record is in §11). **ADDITIVE by construction** — the five fenced crates byte-identical and `SEMANTICS_REV` unmoved, and the CLI's nine `assert_capture` goldens + 18 `guide_sync` tests are how that is known rather than believed. **The layer ROUTES, SCOPES and SERIALIZES and computes nothing about the game** — every model is `screen_model`'s, every word is `describe`'s, every move goes through `Session`'s legal-list gate; a duplicate here would drift and the two frontends would disagree about a rule. `screen_model.rs`'s own module doc names "a later API or GUI layer" as the reason for its import fence, so the port is serde derives plus a handful of `pub(crate)` → `pub`, never an extraction.
  - **One layer, several hosts.** Every game and house route is a typed `pub fn` over `&Games` behind ONE route table and ONE `api::dispatch` (M6.5a), whose parsers make the same calls axum's extractors make, so every 400 sentence is axum's word for word (pinned against axum's own `body_text()`). axum is one host — the NAS/Docker binary, which stays the self-host path — and `crates/yokohama-wasm` is a second: ONE `Games` over `MemStore` with `NoSignal`, `NoArchive` and a settable clock, behind seven `wasm-bindgen` function exports (eight with `debug_trap` in a build with the `debug` feature) that are thin wrappers over pure-Rust `_inner` functions, called from the dedicated Web Worker `web/src/local/worker.ts` — all but `init_diagnostic` (security S1a), whose only callers are the node corpus replay's harness, `web/src/local/corpus.node.test.ts` (the S1 stack review's DC-F8 corrected "six" and "only"). Cloudflare is the third (M6.5c): a stateless Worker that verifies Access's assertion and forwards by NAME to SQLite-backed Durable Objects — a `Table` per table, ONE `House` for the lobby and the house chat, an `Archive` per caller — each running its own instance of `crates/yokohama-worker`, a `cdylib` over the layer without its server half, whose sixteen `wasm-bindgen` exports are called only from `worker/`'s shell (authority: `docs/plans/2026-09-22-web-frontend-m6.5c-objects-spec.md` §2, read through its §10; operations: `worker/RUNBOOK.md`). The platform sits behind seams on `Games` — `Signal`, `Clock` and `Archive` (`Signals`/`now_unix`/`DirArchive` under the `server` feature) — and `platform_calls_stay_behind_the_server_feature` reads the crate's own source and ENFORCES one `#[cfg(feature = "server")]` per platform-calling item; the wasm crate's `this_host_makes_no_platform_call_but_the_clock_and_the_console` holds that crate to the clock, the console the layer's log writes to, and the bindgen glue. **A HEAD takes its GET's arm** and leaves bodiless, a refused one too — an unknown path's 404 included, since S1c's final wave: `find` folds HEAD onto GET, and `answer` picks its arm by the SAME folded method (security S1c; before it a HEAD of a two-method path took the other arm, and the creator's HEAD of a game deleted it — pre-existing, found by Task 3's implementer), so a HEAD never runs a write arm. **An `{id}` the store would refuse is `api::dispatch`'s 404** (`store::is_safe_id`; security S1c, finding B8), in the words the layer uses for an absent game, before the layer asks for the identity and before any handler — it was the store's 500, and a 16 KB one reached the lock map as a key.
  - **Identity** (`identity.rs`): `YOKOHAMA_WEB_IDENTITY` = `open` | `cf-access` | `worker`, with **NO default — an unset variable exits 1**, because a server that guesses its own door is a server whose door nobody wrote down. Each mode reads exactly ONE header and no other (`X-Yokohama-Claimed-User` / `Cf-Access-Authenticated-User-Email` / `X-Yokohama-User`), so a forged header for another mode changes nothing; `User::parse` trims and lowercases ONCE, so a seat is the same seat on the next request; under `worker` the literal `anonymous` counts as ABSENT, which is what makes an unprotected Worker fail CLOSED. **`open` is the self-host door and also the dev door, not a security boundary** (anyone who can reach the server may use any name), and it is the `open-door` cargo feature: a public build (`--no-default-features --features server`) REFUSES `YOKOHAMA_WEB_IDENTITY=open` by name. Every payload the server builds is built for the caller.
  - **The store** takes a typed `Doc` on every call — `Record`, `Table` (`<id>.table.json`), `Chat` (`<id>.chat.json`) and `House` (`_house.chat.json`; `is_safe_id` refuses a leading underscore, so the underscore IS the reservation) — with `write_if_version` and a typed `Conflict`/`Io`. The kinds share one directory, so `is_safe_id` refuses any id ending in a `RESERVED_ID_SUFFIXES` entry (`.table`, `.chat`; case-insensitively, because APFS and NTFS fold case), and **a new document kind needs a new reservation** — the derivation assert compares the two lists' LENGTHS before it zips, so it says so. `check_house_id` is one helper called from `FsStore::path` and from both `MemStore` entry points.
  - **The table document** (`table.rs`) is who may sit here: seats `Human { user, name }` | `Bot` | `Open` (`user` is the key and `name` only a label), the keeps, the setup `seed` (which lives here and NOWHERE on the wire), a `status` of `Open` | `Dealing` | `Playing`, an optional `Lock { salt, hash }` (16 OS-entropy bytes and SHA-256(salt ‖ password), compared by a fold of XORs), the `unlocked` roster of watchers who gave the password (capped, never on the wire), and a `TurnMirror` of `to_move`/`over`/`winner`, the recorded `bot` (M6.5c2) and `has_events` (cycle E: whether the record holds an event — a bit, so it changes once per game and costs one write) — **a cache** that `persist` refreshes, whose conflict is IGNORED, and which exists so the lobby is built from table documents rather than rebuilt sessions. **"over" is NOT a status**: it is read from the session, because a stored copy goes stale. `TABLE_SCHEMA` is **3** and every earlier binary refuses a schema-3 table, so **rolling back across M6.5a is a SCHEMA rollback** (`deploy/RUNBOOK.md` §5). **Every field read out of a stored document is an INPUT**: `check_shape` bounds each one (`players`, `start_seat`, every `keeps[i]`, `to_move`, the lock) because it runs under the table's lock, where a `PlayerId::new` panic poisons the mutex and takes the whole process out. `games.rs` is the record lifecycle and `tables.rs` the table lifecycle: `join`/`keep`/`settle`/`finalize`/`flip_to_playing`/`delete` hold the TABLE's own lock and `create` alone the global `table_lock` (a drawn id is not yet one table), which is why `delete` tombstones BEFORE it unlinks. **A table's lock entry lives only while a writer is inside `Games::with_table_lock`** (security S1c, finding B8): the seven writers — `join`, `keep`, `settle`, `unlock`, `delete` and the chat's append and delete; `finalize` and `flip_to_playing` run inside `settle`'s or `keep`'s — READ the table before they lock (six through `require_table`, `settle` for itself), so a fabricated id is a 404 that never makes an entry, and hold the lock only through the helper, which takes the entry, runs the writer, lets go of its clone and prunes the entry when the map's is the last reference (`prune_lock`), on every return, a refused write's included, and on a panic's unwind (a drop guard, since S1c's final wave); `tables.rs` calls no `lock_for(` of its own, which a source-scan cell pins.
  - **Seats, the deal, and who may read.** A create answers 201 at `open` (a seat still open) or `dealing`, and the join that fills the last seat flips the table to `dealing` in the same write. Each seat reads only its OWN two cards from `…/deal` — another seat's deal never reaches the wire (`DealView.cards` is the caller's own, and null together with `seat` while they wait; no payload carries another seat's cards or keep) — and **the technologies and goals are withheld until the choice** (`withhold_until_the_choice`: a VIEW, not a rule, because the owner's edition takes the secret choice before they are dealt; the seed, the draw order and `SEMANTICS_REV` are untouched). A caller keeps only for a seat they hold — the seat is checked BEFORE the status, so a stranger's keep is a 403 at every status and learns nothing — and the LAST human keep finalizes record-first. **`admitted(state, id, user) -> (TableDoc, Viewer)`** is every route's door: a seat holder at any status; ANY signed-in caller at an `open`, `playing` or finished table for `table` (locked ones included — R-3.13's widening; `table_for_anyone`), and at an `open` table for `events` and `stream`; nobody without a seat at `dealing` (nobody watches a deal); a `Spectator` at `playing` or over once the table has no lock or their email is on `unlocked` (`POST …/{id}/unlock`); and a locked table's reads refused with "this table is locked — unlock it first". **`viewer_seat`** is the acting seat when the caller holds it, else the caller's lowest, so `…/at/{k}` is the caller's own seat at every `k`; masking is `SeatFacts`' — the CLI's own mechanism, widened by `Repl::index_placements_for`, never re-implemented here. **What a stranger learns at a `dealing` table, by design** (finding D10): `…/table` refuses them, and `join`/`unlock` answer `409` with `status: dealing` — a table filling its seats is not a secret, its deal is. **Two rules of security S1a:** an undo whose unit drew from a hidden deck is refused at a table of more than one person (`api::UNDO_DREW`; R-SEC8(a)), and a creator's seed is honoured at a SOLO table only — every human seat theirs, none open (`tables::SEED_NOT_SOLO`; R-SEC8(b)); the fixtures opt into `SeedPolicy::Diagnostic` by name, the Worker's pool through `YOKOHAMA_DIAGNOSTIC_SEEDS` (§12), the browser host's harness through its `init_diagnostic()` export; the NAS binary never.
  - **Spectators, the acting seat, and undo.** A spectator's projection is a NON-ACTING seat's frame: `facts_for(Spectator)` hides every hand, and the projection DROPS the `Hand` panel (`seat: null` on the wire), because a hidden hand still yields a panel that would single out one seat as "yours". **A spectator writes nothing but chat**, and the write sweep proves it behind a store that PANICS on any record read, so "refused before the handle is touched" is a crash and not a sentence. **The acting-seat fence on `input` NEVER drops for a non-acting caller at ANY status** — at game over and lockdown only the 403's wording changes. **Undo** (R-P6): at a table with ONE distinct human email it is the CLI's undo; otherwise only while the trailing event's mover is the caller's seat AND `current_player` still is (replay-derived from `record::state_at(record, len-1)`, checked BEFORE the fence so the answer is always in R-P6's words), and at a FINISHED shared game **nobody undoes**, and no undo of a shared game crosses a draw — the `admitted` bullet above. **Since security S1b the session keeps a checkpoint ladder** (finding A3; `Session::state_before`, `fold_to`): the state at every multiple of `CHECKPOINT_EVERY` (64) events, kept as `from_record`'s fold passes one, as a move lands on one and as a position read passes one. A rebuild (`from_record`) still folds the WHOLE record from setup, through the predicate fold `Session::fold_event` (the untrusted-record replay's own accepted set), and keeps a state every sixty-four events as it goes — the ladder is never serialized, so each rebuild re-cuts it; a position (`/at/{k}`), a run and an undo then fold at most the events since the nearest kept state, not the whole record from setup. An undo drops every rung past the popped length, and the shared-table undo's own guard (the mover's state before the trailing event) folds from the ladder too.
  - **The ONE mutation is `POST /api/games/{id}/input` over `Repl::step`** — `step` IS the state machine and a second dispatcher would fork the option numbering — **fenced by `grammar::is_gameplay_line`, an ALLOWLIST**: `step` is the TERMINAL's front door and also answers `save <path>` (an arbitrary filesystem write) and the sticky overlay words (`?`/`index`/`orders`/`techs`/`goals`/`sitecards`/`view`) after which a NUMBER selects a card rather than a move. TWO rules, not one: a HEAD may only be a listed word or a number/area, because `save` and `view` are ordinary alphanumeric words a single permissive rule lets through. What those words reached are read-only GETs instead: `…/ports`, `…/labs`, `…/areas`, `…/log`.
  - **NO play payload carries the setup seed** — hidden-set member #1 (`game/observe.rs`), which regenerates both decks, the boxed pile, the board and every deal. `TitleModel::seed` is `Option<u64>` (the CLI passes `Some`, this crate `None`), `ClientState` has no seed field at all, and default game ids keep the `sim-{…:016x}` shape but draw INDEPENDENTLY of the seed. Two fences that are deliberately NOT the same check: the server searches the committed corpus for the VALUE (the pin above, whose anti-vacuity partner asserts the seed IS in the stored table document and NOT in the create's reply), and the client asserts the SHAPE (`web/src/wire/contract.test.ts`). The one place the value crosses the wire is INBOUND, in `POST /api/games`, where `WireSeed` serializes as a STRING: a `u64` through a JS number rounds silently past 2^53 and deals a different game.
  - **Persistence: nothing exists only in memory, with three named exceptions.** Every applied move the server acknowledged is persisted as its `GameRecord`, and an absent handle is rebuilt through `Session::from_record`. What does not survive a rebuild: `Repl::sub` (an open multi-step picker — `Input::expect` exists for exactly that case), `Repl::privacy`, and any move whose WRITE failed, which is why the reply carries `APPLIED BUT NOT SAVED` out loud instead of reporting a refusal the server did not make. `Games::persist` stamps the terminal digest through `Session::to_record_json` (serializing `record()` directly would disarm the engine's own provenance refusal), compares record identity by seed FIRST (a name is not a game), and then **COMPARE-AND-SWAPS against a digest of the exact JSON this process last wrote or read**, holding the lock across the read, the compare and the write — an undo POPS events, which a length test cannot tell from a stale handle. It DETECTS a cross-process conflict and does not PREVENT one; where this process has no base it falls back to the length test. A CONFLICTING write EVICTS the handle so a stale `Repl` cannot go on answering 200; an I/O failure does not; `create` holds its own lock across check-then-write.
  - **Transport** (`signal.rs`): `Signals` holds one `tokio::sync::watch` channel per table and one for the house, bumped only in success arms, and **a bump follows its write and never precedes it** — proven by gated cells that park the real write and read the receiver quiet. `GET …/{id}/stream` is server-sent events: the current `Events` on connect, one `event: signal` frame per bump, `event: end` on a delete, a comment heartbeat every 25 s (under the edge's 100 s), no `id:` or `retry:` line, and no game lock held across an await; a 403 or 404 after connect ends the stream — one `end` frame with `gone`, marked last, after which `UntilLast` closes the body (security S1c, finding D1; before it the `gone` frame was written again on every later bump, an activity oracle on a table that had refused the caller) — and any other error writes a comment the client drops and stays open. **`api::events_at` makes `dispatch`'s `{id}` check before any store read** (security S1c, finding B8), because the NAS answers the two transport routes outside `dispatch`; so the Worker's table object, whose module calls `events_at` too, refuses an unsafe id's socket upgrade as it refuses an unknown id's: accepted, ended with the layer's sentence, closed 4404 — for an id of at most 64 bytes, which is what reaches a table object; a longer name the shell routes to the house (`worker/src/route.ts`), whose `dispatch` has no transport row and answers its `no such endpoint` 404 unupgraded, never reaching `events_at`. `GET /api/stream` is the house channel, `{seq, chat, rev}` and silent on connect: the lobby re-lists on a frame whose `seq` moved, or one that moved nothing it recognises, and a frame that moved only `chat` or `rev` — a house message or its delete — re-lists nothing (cycle E, R-E9). `SIGNAL_KIND` is `"sse"` on the NAS, MEASURED through the tunnel both ways (M6.3 close §2.1); **the held-request arm is RETIRED since M6.5c2 cycle D (R-D5)** — `GET …/events` answers at once on every host, its `wait` and `after` parsed and ignored (a `wait` above 25 is still a 400); on the Worker it is `"ws"` — a hibernatable WebSocket carrying the SSE frames' data as `{"event","data"}`, one frame per socket per reply, each computed for that socket's own viewer, with `ping → pong` answered at the edge without waking the object. **The client reads the stream with `fetch`, not `EventSource`** (which cannot carry this server's identity header; `web/src/sse.ts` is the line parser), `usePolled` arms NO timer while connected on the stream arm — the socket arm's one timer is its 30 s keep-alive, which stops at hang-up and sends only while the socket is OPEN; after a close it did not make, the socket arm probes ONCE through the source's own `once()`; and no stream or socket opens before the deployment's transport is known (a wait bounded by `BOUND_MS`, M6.5c's I-86) — a browser holds ONE stream per VISIBLE tab and none in a background tab (R-P8), and a game screen holds its stream at every status of the game while visible — `send` parks any frame that lands while it posts, so a self-bump is never walked as an opponent's move. **A consumer's `active` must not toggle on its own handler**: that is a poll's reason, and on a held connection it reopened the stream once per applied move.
  - **The NAS runs every dispatch on the blocking pool and the five replay routes behind a two-permit gate** (security S1b, findings A2 and D6; `lib.rs`'s `adapter`). The layer's call takes a game's lock, reads a store and may replay or search, and inline on a runtime worker a slow one stalled every other task on it, so the adapter hands `api::dispatch` to `spawn_blocking`; the `events` read and the stream's per-bump reading go to the pool the same way (the `events` read's hand-off has its catcher since security S1c, `the_events_reading_leaves_the_runtime_thread_free`). The five routes are `api::REPLAY_ROUTES` — `POST /api/archive`, `GET …/at`, `…/at/{k}`, `…/suggest` and `…/why` — and never `input`: a move must land while a burst of replays waits. A request to one takes one of `REPLAY_PERMITS` (2) permits, waiting at most `REPLAY_WAIT` (2 s), and past the wait the answer is a 503 with `Retry-After: 1` in the adapter's own sentence, with nothing of the layer run; a HEAD of a gated GET is gated with it. **The body is read BEFORE the permit** (bounded at 2 MiB by the adapter, by design: a permit taken before the read would be held for a whole upload, so two slow uploaders could hold both for as long as they trickle), and the permit moves into the pool's closure, so it is held for the dispatch's whole run, **a caller's departure included**. **A request whose identity did not resolve takes NO permit** (security S1c, S1b's residual): the five routes all need an identity, so the layer answers its 401, or B8's 404 for an unsafe `{id}`, having replayed nothing, and a refused caller never queues behind a real one. The route's own refusals — a missing game, a stranger — stay under the permit, because behind Access every caller is signed in, so such a request still queues (first in, first out). The gate is the NAS's and not the layer's: the Worker's object and the browser's Web Worker run no gate. The knobs are plausibility bounds (§15).
  - **A frame lists the folded, capped legal list** (security S1b, finding A3; `client::folded_legal_capped`): every family of the factored action source in the generator's order, the retreat family at its recover-nothing member alone and the whole capped at `OPTIONS_CAP` (4,096). ## 6. What a save file says

Every record the web lane writes is the engine's own `GameRecord` — the JSON the CLI's `save` writes, which the
CLI resumes and `why` reconstructs. For an evaluation pipeline, this is what it can rely on:

| fact | field | written by |
|---|---|---|
| the rules | `semantics_rev`, `rules_hash`, `terminal_digest` | every record since Phase 2.9; `replay_strict` gates on them |
| the exact bot: its identity, version, every knob and its seed | `run.seats[i]`: `controller`, `version`, `params`, `agent_seed`, `observation` | every game the table layer finalizes (M6.1 on); an all-human game carries a `human` entry per seat |
| the release that wrote it | `engine_version` | always; meaningful from `v0.6.0` on (§7). Provenance, never a compatibility key |
| where it was played | `run.run_id`: `web/server` (the NAS or any self-host), `web/worker` (Cloudflare), `web/browser` (a single-player game in a browser); the CLI's BGA importer writes `bga-import/<table>` | every game finalized since M6.5c2's first deployment (2026-09-28: the Worker's twenty-first, the NAS's fourteenth) |

- **Key a record** by `(semantics_rev, rules_hash)` for whether it replays; by
  `run.seats[i].(controller, version, params)` for which bot played; by `engine_version` for the release; and by
  `run.run_id` for the host.
- **The bot's label** ("V4") is derived, never stored: `crates/yokohama-web/src/bots.rs` maps a recorded
  `(controller, version, params)` through `Contestant::from_parts`.
- **A game that is not over opens on the web exactly when this build's CLI resume reconstructs its EXACT recorded
  bot** (R-F4, amending R-6.5c2.10 forward; cycle F). The layer asks the CLI's own resume,
  `BotSeats::from_provenance`, so the two cannot disagree: a seat the CLI would resume as a human, or one beside a
  drift warning, refuses the game with the CLI's own reason — "This game was played against {played}. This server
  can't continue it: {why}" — and every other seat plays as the bot it recorded, whatever the production bot is. A
  finished one opens, scores and downloads. The CLI still loads either, where a foreign bot's seat resumes human with
  a warning. What this asks of the V5 ship is §15's.
- **Before M6.5c2's first deployment:** a record carries no `run_id`, and a table dealt earlier carries no `bot`
  in its mirror until its next move. A finished one never gains it.
- **`run` travels byte for byte through every save path** (pinned in M6.5c2): the store, the record route
  (`GET /api/games/<id>/record`), the archive on both hosts (`rev7/over/`, `rev7/abandoned/`,
  `browser/<caller>/rev7/…`), the browser's IndexedDB, the export, and the backup envelope.
- **A record carries its setup seed**, which regenerates every hidden card. Treat a save as the whole hidden set:
  saves go to gitignored places (`docs/temp/owner-games/`), never a tracked one.

## 7. The release-version rule

**One release number** (R-6.5c2.19, the owner): the root `Cargo.toml`'s `[workspace.package] version`, which
every crate inherits, and both npm packages' (`web/package.json`, `worker/package.json`) — `0.6.2` at this
writing. The cell `the_two_npm_packages_carry_the_workspace_version` (`crates/yokohama-web/src/lib.rs`) holds them
together.

**Bump it at every release that can change what a save means or which bot plays** — the AI lane's V5 ship
included. **Tag `vX.Y.Z` on the commit the hosts run:** master's, after the merge — or, on a stack that merges at its
wrap (security S2), the deployed branch commit, which the wrap's merge brings onto master (the owner, 2026-10-11:
D-7) — with the release published before either deploy. The tag is annotated, its subject
`Yokohama CLI vX.Y.Z — <headline>`. It runs `.github/workflows/release.yml`: the CLI built for Linux, macOS and
Windows, its tests and the `piped_dogfood` gate, then `gh release create` from the tagged commit.

**The bump, as the move to 0.6.0 measured it:**
1. `Cargo.toml`'s version, then `cargo update --workspace --offline` — the nine members' lock lines, and nothing
   else.
2. `npm version X.Y.Z --no-git-tag-version --ignore-scripts` in `web/` and in `worker/` — each `package.json` and
   its lock's two root lines. A third-party package that happens to share the old number is untouched.
3. `UPDATE_WIRE_FIXTURES=1 cargo test -p yokohama-web --test wire_fixtures` for health's `server_version` and
   `archive-walk.json`'s records, AND `UPDATE_WIRE_FIXTURES=1 cargo test -p yokohama-web --lib backup` for the
   envelope's `app_version` (trap 30). READ the diff: the version and nothing else.
4. `deploy/Dockerfile.runtime`'s example tag.
5. Before the suites, `cd web && npm run build:wasm` and `cd worker && npm run build:module:debug`: a stale module
   answers the old version, and goes red.
6. Before the next live replay, its reset recipe (`worker/RUNBOOK.md` §7, "The replay's reset").
   `archive-walk.json`'s records changed, so the first sends meet a 409.
7. After the deploy, every older game would draw the engine-version drift line. The layer drops that one line
   (`client::without_version_drift`); the CLI shows it, by design.
8. The deploy records name the new NAS tag and the Worker's `server_version` reading.

**A new bot is a web change too:**
- a new `Contestant` or `NamedIdentity` variant does not compile in `crates/yokohama-web/src/bots.rs` until it has
  a label — one line, since the match has no `_` arm;
- re-pointing `PROVISIONAL_DEFAULT_BOT` fails `wire_fixtures` until `web/src/wire/production_bot.json` is
  regenerated;
- a V5 build plays V4's unfinished games on the web exactly when it still derives V4's exact descriptor (§15); the
  admission is in place since 2026-10-01 (`GRANDFATHERED_NAMED_IDENTITIES`), and a re-point appends the identity it
  ships there, never removing one.

## 13. The API map

Every route, in one table (R-6.5c2.45). **The host** says who answers it: `layer` is the table layer's
`api::dispatch`, the same code on every host — the NAS through axum's adapter, the Worker inside its objects, the
browser inside its Web Worker; `axum` is the NAS/Docker binary's own; `worker` is the Cloudflare shell's own;
`browser` would be the local host's own, and it has none. **Who may call it** uses the layer's door:
`admitted` is a seat holder at any status, any signed-in caller at an `open`, `playing` or finished table for
`table` (locked ones included, R-3.13) and at an `open` table for `events` and `stream`, nobody without a seat while
the table is dealing, and a spectator at a playing or finished table that has no lock or that they unlocked. With
`YOKOHAMA_WEB_MULTIPLAYER=off` every `/api/games…` and `/api/chat…` row and the three transport routes are gone. The
cell `crates/yokohama-web/tests/lane_document.rs` holds this table to the code (§2).

**Every `layer` row whose path carries `{id}`** answers an id the store would refuse (`store::is_safe_id`) with the
layer's 404, `no game named "<id>"`, before the layer asks for the identity and before any handler runs
(`api::dispatch`; security S1c, finding B8) — it was the store's 500. The transport rows make the same check in
`api::events_at`, which the NAS and the Worker's table object call outside `dispatch`; on the Worker only a name
of at most 64 bytes reaches a table object, and a longer one is routed to the house (`worker/src/route.ts`),
whose `dispatch` has no transport row and answers `no such endpoint` unupgraded. Each row says how its host
answers it.

**The headers every answer carries** (security S2a; §4). On the NAS every answer — the `layer` and `axum` rows below,
the static release and the fallback — carries the client build's whole header set when its `dist` holds
`headers.json`, and every answer under `/api` carries `Cache-Control: no-store` beside it. On the Worker every answer under `/api` — the shell's own rows and the objects' — carries
`Cache-Control: no-store` and `X-Content-Type-Options: nosniff` from `handle`, a WebSocket's 101 excepted (B9's
Worker half, the S1 stack review's DC-F4), and not the whole set, which `_headers` cannot apply to an answer the
Worker generates. The static release — `/`, `/shell.bin`, every asset, the 404 page — carries the whole set on
both hosts: on the Worker from `_headers`' `/*` block, with no invocation.

## 14. Getting started

Three ways in:
1. **Play at a hosted site.** Open the Worker at `https://yokohama.moore.nyc`, or the NAS at
   `https://yokohama-nas.moore.nyc`, and pass Cloudflare Access's login (the `yokohama` application's policy
   decides who may). The door offers the bot, friends, and the games on this device. "Play with friends" goes
   through `/enter` to the lobby, where "New table" seats you, the bot or an open seat, optionally behind a
   password; share the table's link (`#/t/<id>`), each person keeps one of two dealt cards, and the game begins.
2. **Self-host in Docker.** `deploy/README.md` is the guide: build the image (the five build values are its
   `--build-arg`s, and the Turnstile site key's `--build-arg` stays blank behind Access), then run it with
   `YOKOHAMA_WEB_IDENTITY` set — `cf-access` behind a Cloudflare Access application, the repository's default, or
   `open` for a home network, LAN or VPN — and a named volume at `/data`. `YOKOHAMA_WEB_TABLE_TTL_DAYS` with an
   archive directory turns on the hourly sweep (§10).
3. **Play the bot with no server.** The door's bot card plays entirely in the browser: the layer in a Web Worker,
   every move committed to IndexedDB, the release precached whole so it runs offline once installed. A local game
   calls no server — cycle E read zero Worker invocations for one. Any host that serves the release will do, and
   a build with `VITE_MULTIPLAYER=false` offers only this.

## 15. What is by design

These read like gaps and are not; each is the owner's ruling or a stated property, with its reason.

- **A finished table has no finished-at rule** (straw poll row 74, R-6.5c2.42). The Worker's 90-day idle expiry
  retires finished tables, as the NAS's sweep does where its TTL is set (cycle F, R-F9); a NAS with no TTL keeps
  every table (R-6.5c2.2). A finished table can be abandoned by its
  creator: its game is already in the archive from game over, so the delete files nothing twice (both hosts hold
  the cell).
- **A seat holder's download of a finished record keeps its seed** (row 83, R-6.5c2.42). The route serves a
  seat holder's own FINISHED game only, and the record is the whole game: without its seed it does not replay,
  and the CLI's `why` reconstructs a bot move from the replay (this document's reading of the reason; the owner's
  word on the row is "Agreed", spec §10.11).
- **A finished local game uploads to the archive the deployment configures, with no per-game prompt** (row 91,
  R-6.5c2.42). Where the deployment keeps no archive it goes nowhere; the first time a browser finds an archive,
  every finished local game on the device goes (M6.5b2 close §6.3 item 7), and a player may notice one under
  `browser/<them>/`.
- **A NAS with no TTL keeps its waiting tables.** The 7-day TTL for a table with a seat still empty is inert
  without the table TTL on both hosts (R-6.5c2.42; cycle F, R-F9), so a NAS that sets none sweeps nothing and its
  owner clears a table by its Abandon; the NAS has no marker or operator either way (R-6.5c2.2, R-F10).
- **The sweep decides, then deletes** (cycle F, R-F9; spec §9 F-25). A pass reads each table's last write and
  then calls the creator's delete, which re-checks the seat and the creator but not idleness, so a move can land
  in the seconds between and the table is ended all the same. The move is not lost. The delete lays its tombstone
  before it reads the record it files, under the lock a save holds from its tombstone check to its write: a move
  whose save began before the tombstone has landed by then and is filed with the game like every move before it,
  and a move whose save begins after it is refused out loud ("…was deleted while this move was in flight"). Every
  Abandon runs the same order.
- **A table stuck at its deal waits the long TTL, not 7 days** (ruling 9-b, on cycle E's whole-branch review).
  The 7-day TTL is for status `open` — R-6.5c2.42's "without enough players" — and a `dealing` table has every
  seat taken and waits on a keep, so it expires by the 90-day idle TTL. Cost: a stuck dealing table lingers 90
  days.
- **Four `expect("a game")` sites in the Worker's module** — `crates/yokohama-worker/src/picker.rs` (two),
  `receipt.rs` (one in production, one in a test) — each `handle.lock().expect("a game")` on a module instance
  that is single-threaded by construction (one instance per object, called one request at a time). `lock()` returns
  its `Err` only for a POISONED mutex, and on `wasm32-unknown-unknown` a panic aborts rather than unwinds, so the
  guard is never dropped and the mutex is never poisoned (`crates/yokohama-wasm/src/lib.rs`'s `debug_trap` doc
  says the same); the `expect` never fires short of a defect, which would be worth the host-written 500.

- **No marker on the self-host** (R-F10). A table the NAS's sweep ended answers "no such game", as an abandoned one
  does, and its `sweep-ended` log line is the record; the Worker's expiry leaves a marker sentence where the table
  was. The divergence is the owner's ruling, by name.
- **A TTL without an archive refuses to start** (R-F9). With `YOKOHAMA_WEB_TABLE_TTL_DAYS` set and no

- **The door applies a release; a game never does** (R-F3). On the door a waiting release is applied with no click; on

- **A tab that another tab updated says so** (R-F3; F spec §9 F-7). The door's apply is registration-wide, so a game
  tab beside it is handed to the new worker and plays on out of the retained generation; it draws the same line, as

- **The cost caps are plausibility bounds from measured games, never ceilings a feature may lean on** (security S1b; R-SEC8(e), (f)). `EVENT_CAP` (4,096 events) is seven times the longest finished game people or the bot have played here (595); `ARCHIVE_BODY_LIMIT` (512 KiB) eight times the longest one pretty-printed (54 KB); `QUOTA_RECORDS` (256) and `QUOTA_BYTES` (128 MiB) a caller's share of the NAS archive; `OPTIONS_CAP` (4,096) is above the largest list the generator has offered outside the retreat family (3,303 — the most observed in the pre-flight's sweep of 200 uniform-random games at each player count, at 4P deep in a game no person plays); `CHECKPOINT_EVERY` (64) is a memory choice; `REPLAY_PERMITS` (2) and `REPLAY_WAIT` (2 s) bound the NAS's replay work. ## 16. The metered-action ledger

Every request the client can make to a server, what triggers it and what it is for (cycle F, R-F5; spec §2.5).
**The totals are the harness's — the two-browser tier's watcher, the replay's forces — and the value is the actions
and their ranges**, for the wrap's own analysis and for anyone hosting it: a person at a table makes the same kinds of
request at a person's pace. **The fence, stated once:** on the Worker a door visit with nothing owed, a local game to
its end, and any request for a path the release does not serve cost zero invocations; the first metered request is
`/enter` behind the multiplayer button, a link arrival's first API read, or a finished local game's archive upload (a
door visit that still owes an upload drains it, by design). Its client half is `web/e2e/door_unmetered.spec.ts`
against the local binary — the door asks for the release's own files and nothing else, a local game asks the API
nothing before it ends, and a miss is the 404 page to a fetch and to an uncontrolled navigation and the shell to a
controlled one; the Worker's half is the live reading. **Never count on the 404 page to stop a scanner** (trap 39):
it is what the asset layer answers a miss with — in every shape under an allowed prefix, read 2026-10-01 — and a miss
OUTSIDE the allowed set is the edge rule's to refuse. **The fence against scanners is the edge rule** — ONE WAF custom
rule, a Managed Challenge on every path that is not one of the release's static names, printed from the assets tree
by `worker/scripts/edge-rule.mjs` (the window's recipe, §10), ON with the no-Access door and OFF under Access, which
decides `/api/*`, `/enter`, `/.env` and a random path at the edge with no invocation. Its residual, a miss UNDER an
allowed prefix (`/assets/<miss>`, `/art/<miss>`), passes the rule and costs nothing: the probe read it as the asset
layer's cached 404 page in every shape, 400 requests at 0 invocations (§15).
