Yokohama Assistant — Engineer Primer

A Rust engine, live-tracking CLI, and verification stack for the board game Yokohama · orientation for a first-time reader of this codebase

This repository is a Rust workspace that knows how to play Yokohama (Hisashi Hayashi, 2016, 2–4 players): a rules-complete engine, a command-line driver that tracks or simulates real games move by move, and a verification stack that has been checked, decision-point by decision-point, against a second implementation of the rules written independently from the same rulebook. It is built toward a computer player, so the engine is deliberately shaped as the API a search algorithm will later consume — state is cheap to clone and carries no history. The work follows a three-rung priority order: (1) engine-validated live-game tracking through the CLI, (2) a computer player that provably plays to win, and (3) computer vision, deferred.

1. The workspace at a glance

Five crates. Everything is built on yokohama-core; the arrangement below is the point of the whole design, so it is worth thirty seconds.

yokohama-core — the engine

Serde-serializable state plus two pure functions over it: get_legal_moves(&GameState, &Rules) -> Vec<Move> enumerates every legal move, and apply_move(&GameState, &Move, &Rules) -> Result<GameState, MoveError> returns a fresh state (it clones; it never mutates). apply_move is the checked boundary — it rejects any move not in the current legal list before applying — while apply_move_unchecked is the internal fast path for self-play and the future search, where moves are already drawn from the legal list. Games save and replay through GameRecord, which stamps a rules_hash (which static card/board data produced it), a semantics_rev (bumped for any behaviour-affecting rules change), and a terminal-state digest that replay_strict verifies. Keeping GameState history-free is deliberate: the move history lives in the external record, so search clones stay cheap.

yokohama-cli — the driver

A setup wizard walks you through mode (simulate, or live-track a physical game), player count, colours, seed, and — in live mode — the table's tiles, building sites, and port/lab contents, with a review/edit step before it commits. Then a REPL presents the current player's numbered legal options and applies what you pick, with a/b placement, m assistant-move, and r retreat shorthand grammars for the phases that have too many options to number usefully. It carries save/load/undo/autosave, a reveal choreography for hidden cards drawn during a live game, and a desync tripwire that locks the session if the tracked state and the physical board ever disagree.

yokohama-oracle — the independent referee

A second, independently-authored implementation of the rules, used purely as a referee. It re-implements legal-move enumeration, final scoring with the tie-break, and a prune-free route reference — written from the rulebook, knowledge base, and decision log only, with a types-only dependency on the engine (it shares the data types but reads none of the engine's logic). That independence is the whole idea: two implementations that never read each other's rules code can only agree if both read the actual rules correctly, so a mistaken belief in the engine surfaces as a disagreement rather than as two copies of the same bug. To keep the independence real rather than nominal, every oracle author's file access was audited against the tool calls they actually made.

yokohama-difftest — the harness

Drives the engine and the oracle over the same games under two different play policies and compares them at every decision point: legal-move sets, president-route labels (three-way, against the prune-free reference as well), and final scores and rankings. Any disagreement is written out as a schema-versioned, fully self-contained snapshot of the game state, and a repro subcommand reloads one and re-runs the comparison — so a divergence is a standalone, replayable artifact, not a seed you have to reconstruct.

2. Quickstart

# 1. Install Rust, if you don't have it (rustup)
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
# plain `cargo` works on this project once rustup is installed

# 2. Run the engine's test suite
cargo test -p yokohama-core

#    ...or the full per-edit gate: all four crates, then the lint wall
cargo test -p yokohama-core -p yokohama-cli -p yokohama-oracle -p yokohama-difftest
cargo clippy --workspace --all-targets -- -D warnings

# 3. Run the game driver (setup wizard, then the REPL)
cargo run -p yokohama-cli
cargo run -p yokohama-cli -- save.json     # resume a saved game

# 4. Random self-play: 100 games, 4 players, base seed 0
cargo run --release -p yokohama-core --example selfplay -- 100 4 0

The driver, in one paragraph. cargo run -p yokohama-cli opens the setup wizard, which asks one question at a time (mode, players, colours, start seat, seed, save path, then a mode-specific tail) and lets you review and edit before it starts. In-game, every screen shows a status header, a numbered list of the legal moves, and a hint line; you play by typing an option's number, or one of the shorthand grammars where numbering is impractical — a/b for assistant placement, m <from> <to> for a queued assistant-move reward, and r [id[:n]]... to retreat the President while recovering assistants. Whatever a grammar assembles is matched against the engine's real legal list before it applies, so the tool can never make a move the engine did not offer. The complete tester's guide is docs/cli-guide.md (and a word-identical .html twin).

At the Phase 2.9 close-out the debug suites stood at roughly 940 tests (core 564, CLI 169, oracle 164, difftest 40), zero failures, clippy clean. Those run after every edit. The five heavier release gates below run before a merge or a phase close.

4. How the verification stack works

Two independent techniques, aimed at two different classes of bug.

Self-play fuzzing proves the engine is self-consistent. Fifteen thousand random games (and the 1,500-game CI slice above) run to completion with nine-plus state invariants checked after every applied move — money and goods conserved, hand sizes legal, the turn machine well-formed. This is excellent at catching a state the engine corrupts. But it has a structural blind spot: enumeration and application are the same code reading the same rules, so if both share a wrong belief, self-play cheerfully agrees with itself and sees nothing wrong.

The differential oracle is the tool for exactly that blind spot. Because the oracle enumerates moves from an independent reading of the rules, a shared-wrong-belief bug surfaces as a disagreement rather than staying invisible.

War story. The engine's builder offered only the first empty shophouse slot on a building site — but the site's four slots carry materially different printed rewards, so a player's real choice among them was unencodable. Self-play could never catch it (both sides shared the belief that one slot was enough), yet the oracle enumerated the other slots and the very first differential sweep diverged. The campaign found four such engine bugs this way, plus one bug in the oracle itself.

Divergences are self-contained. When the two disagree, the harness writes a schema-versioned snapshot of the game state at the point of disagreement. cargo run -p yokohama-difftest -- repro [--strict] <artifact.json> reloads that snapshot and re-runs the comparison, so any divergence can be replayed in isolation without reconstructing the game that produced it.

6. Current status & what's next

Status (2026-07-20): Phase 2.9 converged. The engine and the independent oracle agree on every legal-move set (240 of 240 games after fixes), every route label (7,272 organic decision points plus adversarial batteries), and every final score and ranking (540 games). Getting there found and fixed four engine bugs, one oracle bug, and a performance defect, hardened the raw apply path against ill-formed inputs, and produced the owner-adjudicated ruling list. The engine has been the sole legality authority since the prior phase, and the differential harness now stands as a permanent regression net.

Next, in order:

  1. The live gate — tracking one full physical game start to finish through the CLI. This is the Phase-2 acceptance test; the machinery and choice encoding are complete, so it is a scheduling matter for the owner, not an engineering blocker.
  2. Phase 3 — the computer player — a value-function-first ladder toward search (per the project's read of the Catanatron evidence: a good evaluator before deep search). Three handover items are recorded in guidingpath.md for whoever starts it: uniform-random rollouts are a poor playout policy (they over-sample the retreat family), get_legal_moves can materialize a six-figure worst case so search needs a factored/lazy action interface, and training corpora must not be carried across a semantics_rev bump.
